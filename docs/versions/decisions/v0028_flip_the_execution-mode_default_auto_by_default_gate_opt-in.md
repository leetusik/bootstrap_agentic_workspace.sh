### Flip the execution-mode default — `auto` by default, `gate` the explicit approval opt-in

- Date: 2026-08-05
- Status: accepted (flips the default polarity of the 2026-06-20 *Clarify the `do-whole-phase` loop, add an `auto` waiver* decision — see Superseded Decisions)
- Context: Since 2026-06-20 both execution skills defaulted to manual-approval mode — the operator approves each slice's readied plan before its executor runs — with `auto` a strictly opt-in waiver. The operator's standing practice became invoking `auto` on effectively every run, so the shipped default no longer matched actual use and the mode word was pure friction. The operator directed the polarity be flipped in the machinery itself.
- Decision:
  - **Bare `/do-next-slice` / `/do-whole-phase` run `auto`:** plan inline → `Write` `plan.md` verbatim and in full → dispatch the executor, with no plan-approval pause. An explicit `auto` word (and "run unattended") remains accepted as a synonym of the default.
  - **`gate` is the new explicit opt-in** (e.g. `/do-whole-phase gate`) restoring the old loop verbatim: `EnterPlanMode` → read-only research → `ExitPlanMode` for the operator's approval → persist by copying the harness plan file (the confirm-then-copy guard unchanged) → dispatch. Codex, having no plan mode, presents the readied plan inline and waits.
  - **The safety halts do not move:** `pending`, `needs_operator`, `blocked`, and a failed/empty `slice-executor-high` return stop the loop in every mode. Escalation (`mid → high`) re-dispatches without a pause in the default and re-presents the revised plan only in `gate`.
  - **`plan only` is always gated** — it exists to produce operator-approved plans, so it runs the approval gate regardless of the new default; an accompanying `auto` is ignored (previously phrased "never combines with `auto`").
  - **Plan persistence inverts with the default:** `Write` is now the default path (plan mode is never entered, so no harness plan file exists); the copy rule applies in the gated modes (`gate`, `plan only`).
  - **No engine change:** the modes remain skill-prose concepts — `scripts/workflow.py`, the `ready` status, and `validate` are untouched, exactly as the v0007 decision established.
- Alternatives considered:
  - *Keep manual-approval as the default and let the operator keep typing `auto`* — rejected: the standing instruction made the un-defaulted word ceremony with no safety benefit the halts don't already provide.
  - *A persisted config flag (e.g. in `executors.toml`) selecting the default mode* — rejected: mode is a per-run operator choice expressed in the invocation; v0007's "no engine flag" reasoning stands with the polarity flipped.
  - *Retire the approval-gated loop entirely* — rejected: the gate stays valuable for risky phases and for teaching the loop; it just becomes opt-in.
- Consequences: both skills (the Claude copies and the Codex `do-next-slice` mirror, bodies kept byte-identical), both contract files, both READMEs, `operations` v0022, and this entry carry the flipped wording; `WORKSPACE_VERSION` **25** with a CHANGELOG **Migration notes** line, since this is a behavioral change for adopters — a bare invocation now runs unattended.
- Source: operator request (2026-08-05; direct machinery change, no phase)

### Ship opt-in phase-level parallelism — branch-per-phase in a worktree, regenerate-not-merge, deferred doc consolidation, and a PR + CI gate (phase P12)

- Date: 2026-08-04
- Status: accepted (narrows the P-era *"parallel fan-out across slices"* rejection to slice level only — see *Route slice execution through a `slice-executor` subagent*)
- Context: The workspace had exactly one execution stream. `resolve_current` walks active phases by `order` and returns the first non-`done` one, so a second phase could not be started without contending for that global pointer, and a `pending` slice anywhere halted the whole repo. Every state command also rewrites four generated dashboards, so any attempt at concurrent work would conflict on files that are not even authored. The operator asked for genuine concurrency at the **phase** level, with the existing single-stream flow untouched for anyone who never opts in.
- Decision:
  - **The unit of parallelism is the phase, not the slice.** An opted-in phase runs on `phase/P<N>-<slug>` in its own git worktree with its own orchestrator session. Slices inside a phase stay strictly sequential — they build on each other through `phase.md` and a commit per boundary.
  - **Membership is derived from the current git branch**, matched against a `branch` stamped in an optional `phase.json` `execution` block — no marker file. A `git worktree` and a teammate's plain clone of the same branch therefore behave identically, and the stamp cannot drift from where the work actually is. Absence of the block means today's behavior exactly, proven byte-identical for 17 generated artifacts against the pre-phase engine.
  - **A worktree, not a second clone**, so the phase branch shares one object store and one `.git`.
  - **Generated workspace files are regenerated, not merged.** No custom git merge driver: a driver only works where `git config merge.<driver>.driver` has been set in that clone, so it does **not** travel with the repo and silently degrades to a normal merge for everyone else — worst precisely where correctness matters. A conflict in `works/{state.json,index.json,backlog.md,deferred.md}` or `docs/current/*.md` is resolved by taking either side and re-deriving with `parallel-merge-finish`. The only attributes-level rule is `works/events.jsonl merge=union`, because `union` is a git built-in that needs no per-clone config.
  - **Durable-doc consolidation is deferred to a serialized post-merge step on the default stream, and that is engine-enforced.** `docs/index.json` is authoritative hand-merged truth and version ids are allocated `max+1`, so two streams consolidating at once pick the same `vNNNN`; the collision is silent because the existing duplicate check compares the full `vNNNN_<slug>.md` path and two summaries yield two slugs. So `doc-new-version` **refuses** to run on a parallel stream before allocating anything, and `validate` rejects two entries claiming the same number within one doc. A parallel phase's passing review instead *verifies* that `phase.md`'s "Doc impact" list is complete and reports `doc_versions: none — deferred to post-merge consolidation (parallel mode)`.
  - **No `gh` wrapper in the engine.** PR steps are skill-guided, so `gh` auth/output/error handling stays agent territory and `workflow.py` stays offline-testable. `parallel-gate` is the one shared engine-side check that both CI and the agent run before merging.
  - **The CI workflow ships seed-once; `.gitattributes` ships line-merged.** An adopter's CI is theirs to own, so `workspace-ci.yml` is created when absent and never overwritten — but a skipped `.gitattributes` would silently drop the union rule exactly on the repos where a phase-branch merge conflicts, so that one appends its single line into whatever is already there.
  - **The shipped Claude deny narrows from `Bash(git push:*)` to `Bash(git push --force:*)`**, so agent-driven integration can *prompt* for a push instead of being blocked outright with no prompt. Nothing is pre-allowed; the operator still approves each push.
  - **The commit convention gets a scoped carve-out.** Opting a phase in *is* the operator's ask, and it authorizes the engine's one fixed-message stamp commit, the phase branch, its slice commits, and the pushes that open/merge the PR. Outside that documented flow, "no branching, never push unasked" stands verbatim.
  - **The contract routes and the skill explains.** `CLAUDE.md`/`AGENTS.md` take only rules — the carve-out, one compact parallel bullet, the deferral conditions, and the six command names — while the entire lifecycle lives in a new explicit-invocation `parallel-phase` skill.
- Alternatives considered:
  - *A custom git merge driver for the generated dashboards* — rejected: it needs per-clone `git config`, does not travel with the repo, and fails open into a normal conflicted merge for every clone that never ran the config.
  - *A marker file in the worktree to identify the stream* — rejected: it can drift from the branch, and it makes a plain clone of the same branch behave differently from a worktree. The branch name is the truth.
  - *A second clone instead of `git worktree`* — rejected: duplicate object store, and the stamp would have to be synchronized across two repos.
  - *Consolidate docs on the branch at the branch review* — rejected: this is the one operation that cannot be made concurrency-safe by regeneration, since `docs/index.json` is authored truth with `max+1` ids.
  - *Enforce the deferral by prose alone* (the phase's own first cut) — rejected at review: the intent promised the collision "can **never** happen", the feature already engine-guarded its weaker bookkeeping command while leaving the destructive one open, and the failure mode is silent (`validate` passed with two files claiming one version). Closed by a fix slice.
  - *Wrap `gh` in a `workflow.py` subcommand* — rejected: it drags auth and network error handling into an otherwise offline-testable engine for no gain over the skill.
  - *Make parallel mode a default, or auto-start it* — rejected: it stays opt-in, and the engine only ever *suggests* it (a hint from `new-phase` and from `next`, naming `parallel-start`, running nothing).
  - *Refuse `parallel-merge-finish` on a parallel stream, matching `parallel-consolidated`* — rejected deliberately: merge-finish is idempotent and non-destructive, so a warning is proportionate; refusing would strand someone mid-cleanup for no safety gain.
- Consequences:
  - **Engine:** an optional `execution` block on `phase.json` read only through one accessor, stream detection + stream-scoped rebuild, six new `parallel-*` commands, archive gating on pending consolidation, the `doc-new-version` stream guard, and a duplicate-version check in `validate`. `parallel-start` makes the engine's **one** git commit, ever.
  - **Repo/installer:** new `.github/workflows/workspace-ci.yml` and `.gitattributes`, emitted through a single policy helper so fresh install / retrofit / update agree; `.githooks/pre-commit` matches both; `WORKSPACE_VERSION` **24**.
  - **Machinery:** a new `parallel-phase` skill in both harnesses, relays and gates in `create-phase` / `do-next-slice` / `do-whole-phase` / `review-phase` / `archive-phase`, the contract carve-outs, and both READMEs.
  - **Migration:** nothing to do unless you opt in — but an existing adopter must **delete the old blanket `Bash(git push:*)` deny by hand**, because settings merges are additive and a deny can never be removed downstream.
  - **Residual risk:** the CI workflow has never executed on GitHub (pushing is outside a slice's boundaries). It was verified locally with two independent YAML parsers, an ASCII check, branch-name derivation against the real format, and by running every command it invokes. The first real run is the next push; runner `python3` availability and the `origin/<base>` fetch depth are the two unknowns.
- Source: phase P12 (`works/phases/active/P12/`)

### Drop the `low` executor tier — route every slice across two tiers (`mid`/`high`) on a two-value risk vocabulary

- Date: 2026-08-01
- Status: accepted
- Context: The v7 split into three risk-routed tiers put a literal plan-follower (`slice-executor-low`) under `slice-executor-mid`, but the two agent definitions were byte-identical apart from `name`, `description`, and `effort` — the whole difference was a posture sentence and one effort step. In practice the low tier only fit work that barely needed an executor, while the three-point risk scale (`low`/`medium`/`high`) asked the decomposer to grade *difficulty* when what actually matters is *what the slice does*. The operator directed a simpler split drawn on the work itself: `high` takes almost every code-writing slice and every cross-file change without exception; `mid` takes a one-line (or few-line) code edit, or docs.
- Decision:
  - **Two tiers, `kind` still first.** Decomposition and review → `slice-executor-high`, always; a `co-work` design slice is still never dispatched. Otherwise `risk` exactly `low` → `slice-executor-mid`; **everything else** (`high`, legacy `medium`, unset, unknown) → `slice-executor-high`. The v7 "unknown goes up" safe-by-default posture is preserved and in fact widened — only an exact `low` routes down. The orchestrator may still bump a slice up (never down).
  - **The risk vocabulary is `low | high`, and `--risk` defaults to `high`** (it was `medium`) on both `new-slice` and `promote-deferred`. `--risk` is still **not** validated by the engine — that deliberate non-validation is unchanged, and it is what makes the migration free: a pre-v23 slice carrying `risk: medium` simply routes to `high`. A phase's `DECOMP` and `REVIEW` slices are now created with `risk: high` instead of the misleading `low`/`medium` they carried, matching the `kind` rule that already routed them to the top tier.
  - **The surviving `mid` tier keeps its own models and efforts** — economy `sonnet` @ `high`, flex `sonnet` @ `xhigh`, Codex `gpt-5.5` @ `high`. It was deliberately **not** re-cut down to the retired low tier's cheaper values (`sonnet` @ `medium`), because it is now the only non-top tier and absorbs everything the operator rates `low`. `high` is untouched.
  - **`mid` is scoped by work, not by literalism.** It keeps judgment within the plan's intent (it is not the old literal plan-follower), but escalates the moment the slice turns out to be real code writing, spans more than one file, or breaks the plan's assumptions. "Do not grow the job to fit yourself" is stated in the agent body.
  - **The escalation ladder collapses to one step.** `mid → high`, at most **1** escalation per slice (was `low → mid → high`, max 2). The `## Escalation <n>: <from-tier> → <to-tier>` heading becomes the fixed `## Escalation: mid → high`. `slice-executor-high` remains the ceiling and never escalates; a failed/empty `mid` return is still treated as an escalation with no findings, and a failed `high` return still stops the run.
  - **`sync-agents` rejects a retired section by name.** `EXECUTOR_TIERS` becomes `("mid", "high")` and the `executors.toml` parser matches only `[claude.mid|high]` / `[codex.mid|high]`; a leftover `[claude.low]` / `[codex.low]` raises a line-numbered *"the low executor tier was retired in workspace v23"* message pointing at `[<harness>.mid]`, instead of the generic "cannot parse" it would otherwise get. Four agent files now, not six.
- Alternatives considered:
  - *Keep three risk values and map `low` and `medium` both to `mid`* — rejected: it leaves a value in the vocabulary with no distinct meaning, and it routes `medium` (the old default) **down** to sonnet, the opposite of the operator's intent.
  - *Keep `low`/`medium`/`high` and route only `low` to `mid`, leaving the default at `medium`* — rejected for the same reason the default moved: an unrated slice should land on the thorough tier, and `medium` no longer names anything.
  - *Re-cut the surviving `mid` tier down to the retired low values (`sonnet` @ `medium`)* — rejected by the operator: `mid` is now the sole cheap tier, so it keeps `high`/`xhigh`.
  - *Add `choices=["low","high"]` validation to `--risk`* — still deferred, for the third time (v0013, v0017, here). Non-validation is what lets pre-v23 slices keep working untouched.
  - *Delete the retired agent files on `--update`* — rejected, consistent with every prior retirement: updates never delete. Both paths join `OBSOLETE_MACHINERY` and are flagged for manual removal.
- Consequences:
  - **Engine:** `EXECUTOR_TIERS`, `EXECUTOR_PRESETS` (the `low` entry drops from both presets), the `executors.toml` section regex plus a new `RETIRED_EXECUTOR_TIERS` error path, the `executor_agent_files` docstring (6 → 4), the `DECOMP`/`REVIEW` risk values, and both `--risk` defaults with new help text. Machinery: two agent files deleted, the shared tier prose rewritten in the four survivors, the contract (`CLAUDE.md`/`AGENTS.md`, lines 15/16/19/55/61/95), the `do-next-slice` / `do-whole-phase` / `design-cowork` / `update-workspace` skill bodies (+ Codex mirrors), `.codex/config.toml`, and `executors.toml`'s commented defaults.
  - **Installer:** `FIXED_LIVE_FILES` and `MANAGED_FILES` drop the two paths, the emission loop becomes `("mid", "high")`, `OBSOLETE_MACHINERY` gains both retired files, the post-install tier hint is rewritten, and `WORKSPACE_VERSION` goes to **23** with a `## v23` CHANGELOG entry carrying migration notes.
  - **Cost posture:** slices the decomposer would previously have rated `medium` now run on `opus` rather than `sonnet`, so the default cost goes **up** — that is the point. The saving lever is narrower and more explicit: rate a slice `low` only when it truly is a one-line edit or docs.
  - **Incidental fix:** `.githooks/pre-commit` did not match `executors.toml` in its staged-path regex even though `build.py` embeds the file verbatim, so an `executors.toml`-only edit could ship without a rebuild. Added.
  - **Tests:** `tests/retrofit_smoke.sh` asserts 2+2 tier files, the two-tier economy and flex defaults, the absence of both retired files on a fresh install, and the new retired-`[claude.low]` rejection.
  - Supersedes the 2026-07-03 *Split the `slice-executor` into three risk-routed tiers* decision's tier count, routing table, low-tier literalism, and escalation ladder (see *Superseded Decisions*). Ships as workspace v23.

### Retire the bespoke `slice-planner` agent — idle-window preparation becomes an optional, mechanism-free judgment call (phase P11)

- Date: 2026-07-28
- Status: accepted (supersedes the P10 idle-window decision's mechanism and its enforcement claim)
- Context: P10 (v19) shipped a workspace-generated `.claude/agents/slice-planner.md` plus a `do-whole-phase` rule that reads as a mandated sequence — dispatch executor N, then *immediately* dispatch the planner for N+1, with five hard skip conditions. One day later the operator's judgment was that the mechanism should not be prescribed at all: "dispatching explore while meantime planning is not forced. orchestrator can choose to research by it self, or awaiting for the slice to end… I just want to give a free to the orchestrator… it's an option not mandatory. the goal is to make efficient, and high quality work." Plain Claude Code behaviour (the built-in `Explore` agent) covers the delegated-research case without a bespoke file, and P10's own review had already flagged the agent's position **outside** `EXECUTOR_TIERS` as an open gap.
- Decision:
  - **Delete the agent, keep the window.** `.claude/agents/slice-planner.md` is removed along with its three installer touchpoints (`build.py::FIXED_LIVE_FILES`, the explicit `write_text` in `main.py`, `main.py::MANAGED_FILES`) and a **fourth edit added**: an `OBSOLETE_MACHINERY` entry, the only channel by which a v19 workspace is told to delete the file by hand (`--update` never deletes, and `flag_stale_skills()` walks only skill dirs, not `.claude/agents/`).
  - **The rule becomes a permission, not a procedure.** While executor N runs the orchestrator is idle and **may** prepare slice N+1 — dispatch `Explore`, read inline, think it through, or simply wait. `Explore` is named as "the natural fit", a suggestion rather than a requirement: naming no mechanism read as vague, and naming a required one would repeat P10's mistake. Both rewritten surfaces (the `do-whole-phase` bullet and the contract's Hard Rules bullet) open on the permission and put the limits *after* it, framed as constraining **how** the orchestrator prepares, never **whether**.
  - **The invariants that protect the loop stay hard** — read-only, no second executor, never blocks (the executor's completion notification always wins), discarded on any verdict other than `done`, scratchpad-only and never an approved plan, and the operator's approval gate does not move.
  - **The five skip conditions are demoted to guidance**, kept in full but restated as "it usually does not pay off when…" plus "Weigh these; do not tick them off".
  - **The useful half of the deleted agent's prompt is folded into the skill** — bounded advisory brief, hand everything by path, blast-radius exclusions and a "not read / possibly stale" list, never a plan and never a file dump — so the value survives the file's deletion without creating a new managed surface.
  - **Say the weakened guarantee plainly.** P10 claimed the prefetch was read-only *by tool allowlist, not prose*. That is no longer true and the docs must not carry it forward: `Explore` has `Bash`, and inline research is bounded only by the orchestrator's own discipline. **Read-only is now a rule to follow, not a structural property.**
- Alternatives considered:
  - *Keep the agent and merely soften the prose* — rejected: the file itself is what made the mechanism feel mandatory, and it is the thing sitting outside `EXECUTOR_TIERS`.
  - *Keep a hard read-only guarantee by giving the built-in `Explore` a restricted allowlist* — not available: `Explore` is the harness's own agent and is not a workspace-managed file.

### Auto-explain the phase at a passing review — review = validate + consolidate docs + explain (phase P8)

- Date: 2026-07-22
- Status: accepted, then **reversed by P11** (2026-07-28, v21) — the review no longer explains, and the KB-repo commit carve-out is gone; see *Take auto-explain out of the phase review* above and *Superseded Decisions* below

None found, or the skill's own KB probe returns `KB_STATUS=unconfigured`/`error` → skip with a note. The explain outcome is one reported line (`explain: saved <url-or-path>` / `skipped (skill not installed)` / `skipped (KB unconfigured)` / `skipped-offline` / `failed (<reason>)`).

On `changes_requested`/`blocked` there is no explainer, exactly as there are no doc versions. The explain outcome **NEVER** changes the `review_verdict` — even `failed`.

Only that last path needs an exception. The executor's "never commit" rule gains one **narrow** exception — a **review** slice's auto-explain offline fallback may run `git -C <KB_ROOT> add/commit` **only** in the separate KB repo, **never** in this workspace's repo and **never** any `git push`. Rationale: the "orchestrator owns commits" invariant protects *this workspace's* slice boundary; a commit in a *different* git root doesn't cross it, and the skill's offline path is designed to always fall through to a durable, committed save. Codex asymmetry accepted: under `workspace-write` the fallback can't write outside the workspace, so the Codex review treats it as an automatic skip.
- Alternatives considered:
  - *Orchestrator runs explain inline* — rejected: bloats the main thread with a ~500-line HTML generation, the opposite of why execution is delegated.
  - *Duplicate the skill's procedure into the machinery* — rejected: guaranteed drift from the plugin; the machinery references and follows the installed skill instead.

### Wire `/explain` to the KB document API — API-primary save path, manual flow demoted to unreachable-only fallback (phase P6)

- Date: 2026-07-02
- Status: accepted
- Context: The knowledge repo (`~/projects/personal/knowledge`) finished its API track: a compose service on `http://localhost:8766` whose `POST /api/documents` performs, in **one locked call**, exactly what `/explain` steps 5–7 hand-rolled — writes the convention file `docs/<project>/<date>-<slug>.md` with frontmatter, inserts the Recent bullet in `docs/index.md`, upserts the SQLite row, and makes the scoped git commit `docs(<project>): add <slug>` (staging only the files it touched, never pushing). Keeping the hand-rolled steps in the skill duplicates that logic and lets it drift from the API's conventions.
- Decision:
  - **API-primary via two spelled commands.** Steps 5–7 collapse into one save step: the agent writes `body.md` (the document **without** YAML frontmatter, starting at the H1 — the API writes frontmatter itself) and `meta.json` (exactly `title` / `project` / `tags` / `source_repo` / `co_authored_by`; `date` / `slug` / `overwrite` / `commit` left at API defaults) into a temp dir, then runs a spelled `python3 -c` one-liner to merge them into `payload.json` and a spelled `curl -sS --max-time 5 … --json @payload.json http://localhost:8766/api/documents` to POST. **Quoting-safe by construction:** the document body and title never pass through shell arguments — both travel as files.
  - **Transport-vs-HTTP failure semantics.** curl exit ≠ 0 (connection refused / timeout) = the API is unreachable → fallback. Exit 0 = the API answered → branch on the status code: **201** (write NO file, do NOT touch `docs/index.md`, run NO git; report from the response's `url` / `committed` / `commit_error`), **409** duplicate (report `existing_title` / `rel_path`, ASK before retrying with `overwrite:true`), **422** (fix the payload once if the mistake is ours, else report), **401** (bearer token required). HTTP errors **never** trigger a file fallback.

- Status: accepted

### Clarify the `do-whole-phase` loop, add an `auto` waiver, drop the `plan.md` template, and enter plan mode explicitly

- Date: 2026-06-20
- Status: accepted
- Context: `do-whole-phase`'s control flow read ambiguously — the per-slice "plan → approve → executor" loop and the approval-gate waiver were compressed into one dense bullet, and the waiver was only an example phrase ("run unattended") rather than a named opt-in. Separately, the orchestrator's plan step forced its plan-mode output into a fixed `plan.md` template (`Goal / Scope / Milestones / Validation`) plus per-slice `## Operator Input (verbatim)` / `## Operator Intent (refined)` headings — re-encoding the agent's native plan into a rigid form and duplicating, at the slice level, the verbatim-intent capture that `intent.md` already owns at the phase level. And although the design called for plan mode "by default", the skills only described it in prose, so Claude Code rarely actually entered plan mode — the formal plan-presentation/approval step was routinely skipped.
- Decision:
  - **Name the default loop, and what it does *not* pause on.** `do-whole-phase` advances on its own: after each slice it automatically heads into planning the next — it never pauses for permission to *start* planning. The one pause is the operator approving the **readied plan** before the executor runs: **plan → operator approves the readied plan → executor**, repeated. (`do-next-slice` does the same for its single slice.)
  - **Plan mode is entered explicitly.** Prose alone did not trigger it, so the skills now call the tools: in Claude Code the orchestrator calls `EnterPlanMode` to enter plan mode, researches read-only, then calls `ExitPlanMode` to present the readied plan for approval (its approval prompt *is* the gate); on approval the harness exits plan mode and the orchestrator writes `plan.md` and dispatches. `do-whole-phase` re-enters plan mode for each next slice. `EnterPlanMode` / `ExitPlanMode` are added to each skill's `allowed-tools`. Under `auto`, plan mode is skipped entirely (planning happens inline) — otherwise `ExitPlanMode` would force the very approval `auto` waives. (Codex has no plan mode: it presents the readied plan inline.)
  - **`auto` is the explicit waiver.** The operator invokes the skill with `auto` (e.g. `/do-whole-phase auto`; "run unattended" still counts) to skip that plan-approval pause and run plan → executor straight through. `auto` waives only the plan approval — the safety halts (`pending`, `needs_operator`, `blocked`, a failed/empty executor return) still STOP the loop. Applies to both skills.
  - **`plan.md` is the native plan, no template.** `create_slice` no longer scaffolds `plan.md` from a template (the `works/templates/plan.md` file is removed); the orchestrator writes its own free-form native plan into `plan.md` at the slice's turn, and the `slice-executor` reads it from disk as before. A fresh slice now has no `plan.md` until its turn — which tightens the existing "`DECOMP` creates bare folders, don't pre-fill `plan.md`" rule.
  - **Drop the slice-level verbatim headings.** The `## Operator Input (verbatim)` / `## Operator Intent (refined)` convention is removed; the native plan incorporates any operator note, and the operator's verbatim intent lives in the phase's `intent.md`. The refine → clarify → confirm step for an ambiguous slice note stays — its result lands in the native plan rather than a templated heading.
- Alternatives considered:
  - *Drop `plan.md` entirely and pass the plan in the executor's dispatch prompt* — rejected: the `slice-executor` runs isolated and reads its inputs from disk; keeping `plan.md` as the on-disk handoff preserves that pattern and the durable plan record.
  - *Keep the `plan.md` template* — rejected: it re-encoded the agent's native plan into a rigid form for no gain; the native plan is the plan.
  - *Make `auto` a persisted mode or engine flag* — rejected: it is a per-run operator choice, like the prior waiver; no engine change is needed.
  - *Realize plan mode by forking the skill into a `Plan` subagent (`context: fork` + `agent: Plan`)* — rejected: the orchestrator must stay on the main thread to own workflow state, commits, and the operator dialogue across the loop; a forked read-only Plan agent cannot transition state or commit, and loses the session context. Calling `EnterPlanMode` / `ExitPlanMode` from the main-thread orchestrator keeps the split intact.
- Consequences:
  - `workflow.py` `create_slice` scaffolds only `result.md`; `promote_deferred` tolerates an absent `plan.md`. `works/templates/plan.md` is deleted. The `do-next-slice` / `do-whole-phase` skill bodies (`.claude` ↔ `.agents`), `slice-executor.md`, and the contract (`CLAUDE.md` / `AGENTS.md`) are updated; every change is mirrored into the installer (`bootstrap_agentic_workspace.sh`). `validate` is unaffected — it never checked `plan.md`.
  - The `do-next-slice` / `do-whole-phase` skills gain `EnterPlanMode` / `ExitPlanMode` in `allowed-tools` (Claude frontmatter and the installer's per-skill `tools` field) and call them explicitly to drive plan mode; Codex (no plan mode, no `allowed-tools` frontmatter) presents the plan inline. No engine change. Plan mode adds an approval turn-boundary per slice by design; `auto` removes it.
  - Amends the 2026-06-18 orchestrator/worker decision below: its "Plan mode by default … operator can waive it per run" sub-decision now names that waiver `auto`, and "writes `plan.md`" now means the free-form native plan rather than a templated fill.
- Source: operator-request (direct implementation; not run through a phase)

### Route slice execution through a `slice-executor` subagent (orchestrator/worker split)

- Date: 2026-06-18
- Status: accepted
- Context: `do-next-slice` and `do-whole-phase` previously planned and implemented each slice inline on the main thread, so a slice's full implementation — its file reads, edits, and validation churn — accumulated in the same context that also owns workflow state, commits, and operator dialogue. As phases grow this erodes context hygiene and blurs "decide/verify" from "do". The workspace already passes cross-slice context through a file (`phase.md`), not conversation memory, so a subagent boundary behaves like the session boundary the system already survives — making an orchestrator/worker split low-risk and natural. The payoff is context hygiene plus per-slice checkpoints, not parallelism.
- Decision:
  - **Split the two execution skills into an orchestrator and a worker.** The **orchestrator** (main thread) plans each slice, writes `plan.md`, dispatches the worker, verifies the result, runs `validate`, transitions workflow state, commits, and talks to the operator. The **`slice-executor`** subagent implements exactly one already-planned slice in an isolated context: it reads `plan.md` / `phase.md` / `slice.json` / docs / code, implements, runs validation, writes `result.md`, appends cross-slice notes to `phase.md`, and returns a structured verdict (`status` = `done` | `needs_operator` | `blocked`, plus `summary` / `files_changed` / `validation` / `deviations` / `doc_versions`). One procedure, two entry points: `do-next-slice` runs it once; `do-whole-phase` loops it sequentially.
  - **Verify, don't trust.** The orchestrator re-runs `validate` and the executor's critical checks before `finish-slice` and commit; a failed or empty return means the slice is not done — do not finish, do not commit.
  - **Slice-kind routing.** Only implementation and `fix` slices are delegated. Decomposition stays in the orchestrator (it designs the breakdown and creates workflow state); review stays with the `phase-reviewer` subagent. In Codex (no subagents) the executor's procedure is followed inline via a shared-body host conditional.
  - **Plan mode by default.** The orchestrator does each slice's planning in plan-mode style first (read-only research, clarifying questions, present the plan for operator approval — the existing slice-level refine → clarify → confirm), then exits to write `plan.md` and dispatch. This makes `do-whole-phase` pause at each slice's plan gate by default; the operator can waive it per run.
  - **Full-permission executor.** `slice-executor.md` uses the `opus` model and `permissionMode: bypassPermissions` (autonomous, no prompts), at effort `max` as first shipped — later `xhigh`, then risk-based (`xhigh` default, `high` for low-risk implementation/`fix`; see the 2026-07-01 decision above). The guardrails are the orchestrator's verify-before-commit gate plus the executor's hard Never-list (no commit/push, no workflow state-transition commands, no starting/decomposing another slice).
- Alternatives considered:
  - *Keep implementing inline on the main thread* — rejected: loses the context-hygiene and per-slice-checkpoint payoff; the file-based cross-slice channel makes the subagent boundary cheap, so there is little reason not to take it.
  - *Parallel fan-out across slices (worktree isolation)* — **still rejected, and now scoped: the rejection is slice-level only.** Slices build on each other through `phase.md` and the shared tree with a commit at each boundary, so execution *inside* a phase stays sequential and fan-out remains out of scope unless a decomposition explicitly marks slices independent. The blanket "parallelism is out of scope" this bullet originally carried no longer holds: **v24 ships opt-in parallelism at the *phase* level** — a phase on its own branch + git worktree with its own orchestrator session, a stream-scoped pointer, and a quiet-point merge gate (see *Ship opt-in phase-level parallelism* at the top of this log). Phases are the unit that is genuinely independent; slices are not.
  - *Gate the plan-mode approval only on `do-next-slice` and let `do-whole-phase` run unattended* — rejected as the default: the point of the gate is to ask per slice, so both gate by default, with a per-run waiver.
  - *Keep all durable-doc writes in the orchestrator* — rejected: the executor owns `doc-new-version` for its slice (append-only, never patches old versions, coupled to the code change) and reports the versions; the orchestrator confirms via `validate`, avoiding a round-trip.
  - *Pin the executor to a fixed model id; name the dispatch tool `Task`* — corrected during implementation: the executor uses the forward-compatible `opus` model alias, and the skills allow the dispatch tool by its real name **`Agent`** — a skill cannot spawn a subagent unless `Agent` is in its `allowed-tools` (this also formalizes the previously-implicit `phase-reviewer` dispatch).
- Consequences:
  - New managed file `.claude/agents/slice-executor.md` (added to `MANAGED_FILES`); the `do-next-slice` and `do-whole-phase` skill bodies are rewritten and gain `Agent` in `allowed-tools`. The contract (`CLAUDE.md` / `AGENTS.md`) documents the orchestrator/executor model in *Driving This Workspace* and a Hard Rule. Every change was applied in the installer first, then mirrored to the materialized snapshot (`.claude` ↔ `.agents`), with byte-parity verified by re-generating from the installer; `tests/retrofit_smoke.sh` passes and no real slice was executed.
  - Codex has no subagents, so it gets no `slice-executor.md` file and executes the same procedure inline through the shared skill body's host conditional.
  - No `workflow.py` engine change: delegation is a skill/contract convention, not a machine-enforced invariant. The structured verdict is a reporting convention the orchestrator acts on (`needs_operator` → set the slice `pending` and stop; `blocked` → record and stop).
- Source: operator-request (direct implementation; not run through a phase)

- Date: 2026-06-15
- Status: accepted
- Context: Operator requests enter the workspace as free natural language that can carry grammar slips, awkward phrasing, or genuine ambiguity. The previous flow distilled that raw text straight into a phase `--objective` (or a slice's `## Operator Input (verbatim)` note) with no refinement, no clarification, and no confirmation — so a misread of intent propagated silently into decomposition and every downstream slice, and there was no durable, authoritative record of what the operator actually asked in their own words.

- Alternatives considered:
  - *Store intent as a `## Intent` section inside `phase.md`* — rejected: mixes the immutable verbatim original with the evolving notebook; a separate `intent.md` keeps the original word-for-word and is the literal "store it somewhere and link from `phase.md`".

### Support non-destructive retrofit into an existing repo via `--into-existing`

- Date: 2026-06-10
- Status: accepted
- Context: The installer only scaffolded into an empty directory — it hard-aborts when any managed file exists and refuses non-empty targets without `--force-empty-ok`, and `write_text` overwrites unconditionally. There was no supported, documented way to adopt the workspace into a repo that already has code, a README, `scripts/`, `docs/`, or git history, and no safe story for collisions with existing files.
- Decision:
  - **Extend the installer** with a flag-gated `--into-existing` retrofit mode rather than shipping a separate script or a skill-only staging dance. The fresh-install (no-flag) path stays byte-for-byte unchanged.
  - Retrofit is **non-destructive** and runs in **two passes**: a PLAN pass classifies every managed path with no writes and aborts up front on an unresolvable collision (so the tool never half-installs), then an APPLY pass writes by tier.
  - **Four-tier collision policy:** (1) *skip-if-exists* for pure content; (2) *install the `docs/` and `works/` subsystems only if wholly absent* (gate on `docs/index.json` / `works/state.json`) and gate the installer's final `rebuild`/`validate` to only-installed subsystems — because `rebuild` itself unconditionally overwrites generated files, so skip-on-write alone is insufficient; (3) *additive, idempotent merge* for `.claude/settings.json` (union permissions) and `CLAUDE.md`/`AGENTS.md` (a marked workspace section plus a `*.workspace.md` sidecar holding the full contract); (4) *hard abort* on a pre-existing `scripts/workflow.py`, since the whole runtime shells out to it.
  - **Seed P1 from project state** using only the existing `--phase-name`/`--phase-objective` flags (no `workflow.py` change); the `/retrofit` skill synthesizes them from the README/manifest/language/latest commit. P1 stays `DECOMP`+`REVIEW`-only.
  - Deliver a `retrofit` **skill** (mirrored in `.claude/skills` and `.agents/skills`, explicit-invocation only) that orchestrates preflight → installer → contract reconciliation → `validate` → report, and a committed, non-installed smoke test (`tests/retrofit_smoke.sh`).
- Alternatives considered:
  - *Skill/guide-only staging without changing the installer* — rejected: more fragile and harder to verify deterministically than a flag the installer owns.
  - *Uniform skip-if-exists for every file* — rejected: unsafe, because the installer's final `rebuild` re-overwrites generated `docs/current/*` and `works/*`; non-destructiveness is a property of write **and** rebuild together.
  - *Strict zero-touch (only ever create new files; sidecars + manual merge for everything)* — rejected in favor of additive idempotent merges for `.claude/settings.json` and the contract, for a usable out-of-box result; merges are additive-only and re-runnable with no duplication.
  - *Add an `edit-phase`/`rename-phase` command to reseed P1* — rejected: unnecessary; the existing seed flags suffice and avoid touching `workflow.py` (and its dual-apply surface).
- Consequences:
  - The installer gains a clearly flag-gated retrofit branch; the fresh path is untouched and still validated by a regression check.
  - Retrofit-only artifacts (`CLAUDE.workspace.md`, `AGENTS.workspace.md`) are deliberately **not** added to `MANAGED_FILES` (or the fresh-install guard would false-trip); the new `retrofit` skill's files **are** added so fresh installs ship it.
  - Dual-apply surface: the new skill (live files + `COMMAND_SKILLS`) and, if touched, the contract (live `CLAUDE.md`/`AGENTS.md` + the embedded `WORKFLOW_DOC`); `workflow.py` is intentionally left unchanged. A committed smoke test asserts the live↔embedded copies stay in sync.
- Source: P3 (slices P3.S1 guide+docs, P3.S2 installer mode, P3.S3 skill, P3.S4 verification)

### Phase archiving is manual and explicit, with three first-class operations

- Date: 2026-06-10
- Status: accepted
- Context: A passing phase review marks a phase `done` but should not move it out of `active/`. Operators need control over when phases leave the active set, and the original single-phase archive was framed only as an exceptional "escape hatch", leaving no supported way to archive *some* done phases while others are still in flight.
- Decision:
  - Archiving is **manual and user-requested only**, never automatic. A passing review only marks a phase `done` and leaves it in `active/`.
  - `archive-all` stays the default end-state sweep: archive every active phase at once, allowed only when **every** active phase is done (the last review slice complete).
  - `archive-phase <P>` is promoted from an exceptional escape hatch to a **first-class** single-phase archive (still gated on a passing review; `--force` only for exceptional cleanup of an unfinished phase).
  - A new **`rotate-backlog`** operation archives every phase that is currently done and leaves in-progress phases active, then rebuilds the dashboards — the partial rotation `archive-all` cannot do (it requires all phases done). Shipped as a `workflow.py` command and a skill mirrored into `.claude/skills` and `.agents/skills`.
- Alternatives considered:
  - *Auto-archive a phase when its review passes* — rejected: removes operator control and makes the active set churn mid-work; the operator explicitly wants archiving to be a deliberate step.
  - *Keep single-phase archiving as an escape hatch only* — rejected: with many phases and only some done, partial archiving is a normal need, not an exception.
  - *Add a `--dry-run`/`--force` to `rotate-backlog`* — deferred: by construction it only touches cleanly-archivable phases, so neither is needed yet; revisit if a preview is requested.
- Consequences:
  - Three archive entry points with one shared gate (`_phase_blockers`: all slices done + review `pass`): `archive-all` (full sweep), `rotate-backlog` (partial sweep), `archive-phase` (single). `rotate-backlog` reuses the existing archive helpers; no forked logic.
  - Every rule/skill/tooling change is applied in both the live repo files and their embedded copies inside `bootstrap_agentic_workspace.sh`, and `CLAUDE.md` is kept in sync with `AGENTS.md` (both generated from the same embedded contract).
- Source: P2 (slices P2.S1 engine, P2.S2 skills, P2.S3 contract, P2.S4 this record)
