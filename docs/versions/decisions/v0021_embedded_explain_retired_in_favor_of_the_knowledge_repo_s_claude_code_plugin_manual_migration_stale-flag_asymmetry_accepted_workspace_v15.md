### Retire the embedded `/explain` feature — it ships as a Claude Code plugin now (phase P7)

- Date: 2026-07-21
- Status: accepted
- Context: `/explain` was coupled to the operator's personal Mac from the start — a knowledge base at `~/projects/personal/knowledge`, its document API at `localhost:8766`, a viewer at `localhost:8765`. Two earlier phases had made it tolerable inside the bootstrap: P5 gated it **opt-in at install** (`--with-explain`, default off, source kept live) and P6 wired its save path to the KB document API. But its public-portability half stayed **deferred as D1** (parameterize the KB path/ports so any adopter could use it) — a hard problem to solve inside a bootstrap installer. The knowledge repo has since shipped its own **Claude Code plugin** (its P7, review passed): the explain skill + KB scaffolder, installable via `/plugin`, distributed from one place. That makes the feature portable for real, so carrying an embedded, Mac-coupled copy in every workspace is now pure liability. The operator's roadmap always ended here — "after knowledge claude plugin done, the explain related stuff will [be] discarded from this bootstrap repo" — gated on the knowledge plugin landing first.
- Decision:
  - **Remove `/explain` from the distribution entirely** — a genuine source removal this time, not the P5 install-time gate. Delete the embedded skill copies (`.claude/skills/explain`, `.agents/skills/explain`), the `--with-explain` wrapper flag, and the whole `WITH_EXPLAIN` / `OPTIONAL_SKILLS` install-time filter in `installer/main.py`. Because `build.py` discovers skills from disk (`glob("*/SKILL.md")`), deleting the two dirs drops them from the embedded `PAYLOADS` on rebuild — no build-code change. `--with-explain` becomes an **unknown option** the installer rejects (the wrapper's generic `-*) die` arm). Ships as workspace **v15** (`WORKSPACE_VERSION` 14 → 15 + the `## v15 — 2026-07-21` CHANGELOG entry with Migration notes, all one commit with the rebuilt artifact).
  - **Point users at the plugin.** README.en.md and the CHANGELOG carry the **verified** pointer (read from the knowledge repo's `marketplace.json` / `plugin.json`, not invented): inside Claude Code, `/plugin marketplace add leetusik/knowledge` → `/plugin install knowledge@knowledge`, then `/knowledge:setup` once and `/knowledge:explain <topic>`. Note the namespace change from bare `/explain` to `/knowledge:explain`.
  - **Manual migration; nothing auto-deleted.** On `--update`, a downstream that had `explain` installed keeps its on-disk copies (no longer in `PAYLOADS`, so never re-written, never deleted). The generic `flag_stale_skills` flags them **asymmetrically**: the Codex copy `.agents/skills/explain` (has the `agents/openai.yaml` marker) is flagged stale, while the Claude copy `.claude/skills/explain` (no `disable-model-invocation: true` marker) is treated as operator-owned and left untouched. This asymmetry is **accepted** rather than special-cased — `flag_stale_skills` and `OBSOLETE_MACHINERY` are left untouched (the former is generic and already yields this behavior; the latter is for retired individual files, not skill dirs). The CHANGELOG **Migration notes** instruct existing installs to remove **both** copies by hand and install the knowledge plugin.
  - **Resolves D1 by deletion.** The plugin makes explain portable for real, so D1 (make `/explain` usable by public users) is dropped, not built — the orchestrator ran `drop-deferred D1` after the implementation slice landed.
- Alternatives considered:
  - *Keep the embedded skill and finally parameterize the KB path/ports (build D1)* — rejected: it duplicates, inside a bootstrap installer, exactly the distribution problem the knowledge plugin now solves cleanly from one place; the operator's roadmap called for retirement once the plugin shipped.
  - *Special-case the `--update` stale-flag asymmetry so both copies are flagged uniformly* — rejected as unnecessary machinery: the generic behavior is already correct enough, and a one-line Migration note ("remove both by hand") covers the gap without touching `flag_stale_skills`.
  - *Add an `OBSOLETE_MACHINERY` entry for the explain dirs* — rejected: that list retires individual *files*; stale skill *dirs* are handled by `flag_stale_skills`, which already flags the Codex copy.
- Consequences:
  - **No `workflow.py` engine change** — all edits are installer source + machinery. `installer/wrapper.sh` (four `--with-explain` bits removed), `installer/main.py` (`WORKSPACE_VERSION = 15`; the entire optional-skill block removed so `CLAUDE_SKILLS`/`CODEX_SKILLS` flow unfiltered), the two deleted skill dirs, `tests/retrofit_smoke.sh` (Test 5's default-omit assertions kept as permanent invariants; Test 8 rewritten to assert `--with-explain` is rejected), `README.en.md` (explain rows/prose pruned, plugin pointer added; skill counts re-derived — `.claude/skills/*/` = 15, `.agents/skills/*/` = 14, unchanged because explain had been counted as the separate "optional" extra), `CHANGELOG.md` (`## v15` with Migration notes), and the rebuilt `bootstrap_agentic_workspace.sh` — all in **one commit** (the same-commit rebuild rule + drift guard forbid a split). Root `README.md` (Korean) untouched — its only "explain" is the contract tagline word.
  - Supersedes the P5 opt-in-gate and P6 API-save-path operational truth for `/explain` (operations v0010/v0011): the feature no longer ships from this repo at all. The P5/P6 decision entries below remain as history.
- Source: P7 (slice P7.S1 removal + rebuild; P7.REVIEW consolidation). Gated on the knowledge repo's P7 plugin (review passed) landing first, per the operator's roadmap.

### Drop the `result.md` template — the executor writes a free-form result from scratch

- Date: 2026-07-04
- Status: accepted
- Context: `plan.md` went template-free in the v0007 decision, but `result.md` was still scaffolded by `new-slice` from `works/templates/result.md` — a fixed-section form (Review status / Outcome / Deviations / Validation Run / Files Changed / Doc Versions Created / Roadmap Updates / Retrospective). The operator disliked the result and asked whether to drop the scaffold or fold results into `phase.md`. Inspection showed the template was mostly vestigial: nothing in the engine ever reads `result.md`'s contents (only the path is recorded in `slice.json`), `Review status` dates from the retired per-slice review, and `Roadmap Updates` references a concept the contract no longer has. Meanwhile the executor agent prompts already specify what a result must cover.
- Decision:
  - **No scaffold, keep the file.** `new-slice` writes only `slice.json`; the executor writes `result.md` from scratch at slice end, shaped to the slice — symmetric with the orchestrator's free-form `plan.md`. The executor prompts now say so explicitly and still require the same substance: validation commands + outcomes, doc impact (or doc versions on review), and deviations from plan.
  - **`works/templates/result.md` is deleted** and joins `OBSOLETE_MACHINERY` (flagged on `--update`, never auto-deleted). Ships as workspace v10.
- Alternatives considered:
  - *Fold results into `phase.md` and drop `result.md` entirely* — rejected: `phase.md` is read by every subsequent executor at dispatch, so full per-slice results there would bloat the shared context the orchestrator/executor split exists to protect; the review slice reads each slice's `result.md` (and re-runs the validation commands recorded there), which needs per-slice granularity; and blocker records land per-slice. The existing split stands: details in `result.md`, durable one-line notes in `phase.md`.
  - *Keep a slimmed template* — rejected: the executor prompts already carry the content requirements; a template adds a second place to maintain them and invites stale sections again.
- Consequences:
  - Engine: `create_slice` in `scripts/workflow.py` no longer renders any slice-folder template (a fresh slice folder holds only `slice.json`). Machinery: the six `slice-executor-*` prompts gain the free-form wording, the contract (`CLAUDE.md`/`AGENTS.md`) marks both slice context files template-free, installer `FIXED_LIVE_FILES` / `MANAGED_FILES` / the template emission drop the file, `OBSOLETE_MACHINERY += works/templates/result.md`, `WORKSPACE_VERSION = 10` + the `## v10` CHANGELOG entry. Existing slices' already-written `result.md` files are untouched.
- Source: operator request, 2026-07-04 (direct machinery change on `main`; no phase — durable docs versioned with the change)

### Ship `executors.toml` itself, seeded once with commented defaults — drop the `.example` file

- Date: 2026-07-04
- Status: accepted
- Context: Hours after v8 shipped, the operator observed that the `.example` indirection buys nothing here — the file holds no credentials, so the real file can simply ship. Two hazards to design around: a shipped config file must never be update-overwritten (it is the operator's), and a file shipped with *active* default values would pin those defaults as if the operator chose them — after a future upstream default change, `--update` would refresh the agent files to the new defaults and the pinned file would then tell `sync-agents` to revert them.
- Decision:
  - **The installer seeds `executors.toml` directly** — on fresh install, retrofit, and `--update` onto a workspace missing it — and **never overwrites an existing one**: a new SEED-ONCE class in the update write policy beside OVERWRITE / MERGE / CONTRACT / PRESERVE (retrofit's existing keep-theirs Tier 1 already covers the retrofit case). `executors.toml.example` is dropped and joins `OBSOLETE_MACHINERY`.
  - **Defaults ship commented out** (the `redis.conf` / `sshd_config` pattern): the seeded file parses as empty, so the engine's `EXECUTOR_DEFAULTS` stay the single source of truth and a workspace that never opted into overrides keeps tracking upstream default changes across updates. Deleting the file remains fine (absent = defaults). `sync-agents` now prints the active override count, so a freshly seeded file reads as `executors.toml (0 override(s)) + defaults`.
- Alternatives considered:
  - *Seed with active values (the literal proposal)* — rejected for the pinning hazard above; commented values give the same "the file just exists — edit it and sync" ergonomics without freezing defaults.
  - *Keep the `.example` and gitignore the real file* — already rejected in the v8 decision (committability is half the point); with seed-once semantics the copy step became pure friction.
- Consequences:
  - `installer/main.py` gains the seed-once branch in `_update_handle` and `WORKSPACE_VERSION = 9`; `FIXED_LIVE_FILES` / `MANAGED_FILES` / the emission swap to `executors.toml`; `OBSOLETE_MACHINERY += executors.toml.example`. `tests/retrofit_smoke.sh` now drives a real `--update` twice — no-clobber on an edited file, then seed-on-update after deletion — and the stale flag for a leftover `.example` was probed live. The upstream repo tracks `executors.toml` at commented defaults (the drift-guard caution now reads "keep it at the commented defaults"). Ships as workspace v9.
- Source: operator request, 2026-07-04 (direct machinery change on `main`; no phase — durable docs versioned with the change)

### Move the executor-tier config surface from a gitignored `.env` to a committable repo-root `executors.toml`

- Date: 2026-07-04
- Status: accepted
- Context: The v7 tier config shipped as a gitignored repo-root `.env` (`SLICE_EXECUTOR_*` / `CODEX_SLICE_EXECUTOR_*` keys) with a tracked `.env.example`. The operator asked whether the custom executor settings could be managed with a TOML file instead of the root `.env`. Three problems with `.env` back the switch: adopting workspaces are real applications that commonly already carry an app-level `.env` (dotenv loaders, secrets) — mixing workspace tooling keys into it is invasive, and the secrets convention forces gitignoring; a gitignored file cannot be committed or reviewed as team-shared config; and the flat SCREAMING_SNAKE keys carried a `CODEX_`-prefix asymmetry. TOML is also already native vocabulary on the Codex side (`.codex/config.toml`, `.codex/agents/*.toml`).
- Decision:
  - **Repo-root `executors.toml`** with `[claude.low|mid|high]` / `[codex.low|mid|high]` tables holding `model` / `effort` string keys. Resolution semantics carry over unchanged from the `.env` scheme: missing tables/keys keep `EXECUTOR_DEFAULTS`, values pass through verbatim (aliases, full model IDs — e.g. `fable` or `claude-mythos-5` on the high tier — and `inherit` all work), `effort = ""` omits the effort line (the haiku escape hatch), and an empty model errors.
  - **Committable, not gitignored.** The file holds no secrets; committing it shares the tier setup with the team. The `.env` line v7 added to `.gitignore` is removed. The upstream caution is unchanged: in the bootstrap repo itself keep `executors.toml` absent or at defaults, because a non-default `sync-agents` run mutates the committed agent files and the artifact drift guard rightly blocks the commit.
  - **Strict-subset parser, stdlib-floor preserved.** `read_executors_toml()` hand-parses the documented subset (dotted section headers, double-quoted scalar values, `#` comments — full-line and trailing) rather than importing `tomllib`, keeping the engine's floor at "any python3" (`tomllib` is 3.11+). Every unrecognized line, unknown section, duplicate key, or unquoted value fails with a line-numbered error — typos surface instead of silently keeping a default (the `.env` reader silently ignored unknown keys).
  - **Migration surface.** `executors.toml.example` replaces `.env.example` as tracked machinery; `.env.example` joins `OBSOLETE_MACHINERY` (flagged on `--update`, never deleted); `sync-agents` prints a warning when a leftover `.env` still holds `SLICE_EXECUTOR_*` keys (it is no longer read). Ships as workspace v8, whose CHANGELOG entry also covers the `plan only` / `ready` feature (commit `3104b74`).
- Alternatives considered:
  - *Parse with stdlib `tomllib`* — rejected: raises the engine's Python floor to 3.11 for a 12-key file, and a tomllib-with-fallback dual path would accept different syntax depending on the interpreter.
  - *Keep reading `.env` as a fallback* — rejected: two live config surfaces invite drift and ambiguity about which won; v7 was one day old with no known adopters, so a warning plus a migration note suffices.
  - *Home the file elsewhere (`works/config.toml`, `.claude/…`)* — rejected: it configures both harnesses (so neither tool dir fits) and is operator configuration, not workflow state (so `works/` doesn't fit); the repo root matches the `.env` slot it replaces.
  - *Gitignore `executors.toml` as `.env` was* — rejected: committability is half the point; an operator who wants it machine-local can ignore it in their own repo.
- Consequences:
  - Engine: `read_env_file()` → `read_executors_toml()` in `scripts/workflow.py`, reworded `sync-agents` / `validate` messages, and the legacy-`.env` warning; the patch helpers (`_patched_agent_md/_toml`), the defaults dict, and the advisory drift warning are unchanged. Machinery: `executors.toml.example` (tracked; `.env.example` removed), `.gitignore`, the `do-next-slice` / `update-workspace` skill bodies (+ Codex mirrors), the contract (`CLAUDE.md`/`AGENTS.md`), `.codex/config.toml`, and the README / retrofit-guide / installer-README passages. Installer: `FIXED_LIVE_FILES` / `MANAGED_FILES` / `_is_machinery` / emission swaps, `OBSOLETE_MACHINERY += .env.example`, `WORKSPACE_VERSION = 8` + the `## v8` CHANGELOG entry. `tests/retrofit_smoke.sh` asserts the example swap, the legacy example's absence, and a live override → restore roundtrip through `executors.toml` on a fresh install.
  - Verified 2026-07-04: five malformed-file probes (unquoted value, unknown section, key outside a section, duplicate key, empty model) each fail with a line-numbered error; spaced headers and trailing comments parse; `[claude.high]` `model = "fable"` patches exactly the high tier's frontmatter `model:` line and deleting the file restores defaults idempotently; full smoke suite and `validate` green.
  - Supersedes the `.env` config-surface aspect of the v7 three-tier decision below — the tiers, risk routing, defaults, literal low tier, and escalation ladder all stand (see *Superseded Decisions*).
- Source: operator request, 2026-07-04 (direct machinery change on `main`; no phase — durable docs versioned with the change)

### Split the `slice-executor` into three risk-routed tiers (low/mid/high) with `.env`-configurable models and a failure-escalation ladder

- Date: 2026-07-03
- Status: accepted
- Context: Every slice ran on Opus — `slice-executor` (opus @ `xhigh`) for decomposition/review/non-low-risk slices, `slice-executor-high` (opus @ `high`) for low-risk ones — so easy slices paid top-model cost and latency. The operator asked for three capability tiers to save cost and time while preserving quality, with models **and** efforts configurable via a repo-root `.env`, and an escalation path: when a lower tier can't handle a slice, the orchestrator revises the plan from the failure findings and re-dispatches a more capable tier. Constraint (unchanged from the v0013 decision): a subagent's effort is frozen in its frontmatter at spawn — neither harness has a per-dispatch effort override — so tiers are separate named definitions: 3 per harness, 6 files, byte-identical bodies.
- Decision:
  - **Three tiers, risk-routed, `kind` first.** Decomposition and review → `slice-executor-high`, always; `risk` exactly `low` → `slice-executor-low`; exactly `medium` → `slice-executor-mid`; anything else (high / unset / unknown) → `slice-executor-high`, preserving the v0013 safe-by-default "unknown goes up" posture. The orchestrator may bump one tier UP (never down). Defaults: low = `haiku` with **no effort line** (the Anthropic API rejects the effort parameter on Haiku 4.5, and whether the harness translates frontmatter effort is unverified — the shipped default must not gamble; an empty `*_EFFORT` in `.env` means "omit the line"), mid = `sonnet` @ `xhigh`, high = `opus` @ `xhigh` (unchanged behavior); Codex tiers run `gpt-5.5` @ `medium`/`high`/`xhigh`. The untiered `slice-executor{.md,.toml}` are retired; phase reviews record `--reviewer slice-executor-high`.
  - **The low tier is a literal plan-follower (operator directive, 2026-07-03).** `slice-executor-low` executes `plan.md` step by step — no judgment calls, no workarounds, no improvisation, no deviations. On ANY departure from the plan's assumptions it stops early and escalates with what it observed rather than attempting a fix the plan doesn't spell out. Decomposition therefore rates a slice `low` only when its work will be fully mechanical — `risk` is the phase's main cost lever.
  - **`.env` + `sync-agents`.** New engine command `sync-agents [--check]`: overlays the built-in `EXECUTOR_DEFAULTS` with a repo-root `.env` (`SLICE_EXECUTOR_{LOW,MID,HIGH}_{MODEL,EFFORT}` for Claude, `CODEX_SLICE_EXECUTOR_…` for Codex) and patches **only** the `model:`/`effort:` (`.md`) and `model =`/`model_reasoning_effort =` (`.toml`) lines of the six agent files, atomically and idempotently. Values pass through verbatim (aliases, full model IDs, `inherit` all work); an empty effort omits the line; an empty model errors. `validate` warns (never errors, crash-safe) while the files drift from `.env`/defaults. `.env` is gitignored; `.env.example` ships as machinery (refreshed on `--update`); after `/update-workspace`, `sync-agents` must be re-run since updates reset the agent files to upstream defaults. This is the engine's first write surface outside `works/` + `docs/` — deliberate: the agent files *are* the executor configuration.
  - **Escalation ladder.** The executor verdict gains a fourth status, `escalate`, plus an `escalation` findings field (what was tried, what broke, what the next tier needs, worktree state). Discriminator: `escalate` = a stronger executor given the same files and plan could plausibly finish (capability, broken plan assumptions); `blocked` = no amount of capability helps; `needs_operator` = a question only the operator can answer. On `escalate` — or a failed/empty return from low/mid, treated as an escalation with no findings — the orchestrator appends an `## Escalation <n>: <from-tier> → <to-tier>` section to the slice's `plan.md` and re-dispatches the next tier up (jumping low→high only when the findings clearly show mis-rating; at most 2 escalations per slice; the slice stays `in_progress` throughout — no engine/state change). Gated mode re-presents the revised plan for operator approval; `auto` re-dispatches without a pause while the other safety halts (`pending`, `needs_operator`, `blocked`, failed high return) still stop the loop. The top tier never escalates; a failed/empty high return keeps the old not-done-STOP behavior.
- Alternatives considered:
  - *Keep `slice-executor` as the top-tier name and add only `-low`/`-mid`* — rejected: a permanent asymmetry in every fresh install. Under the chosen full rename, the one stale file an updated workspace can retain (`slice-executor.md`, opus @ `xhigh`) is behaviorally identical to the new top tier, so the migration hazard is benign; `--update` flags it via a new `OBSOLETE_MACHINERY` list (updates never delete).
  - *`haiku` + `effort: high` as the shipped low default* — rejected: the API rejects effort on Haiku 4.5 and the harness's frontmatter behavior for it is unverified pre-ship; operators can opt in via `.env` after the live smoke test proves it.
  - *Fable 5 as the high default* — rejected: 2× Opus price against a cost-saving goal; reachable any time via `.env` verbatim pass-through.
  - *Route unknown risk to mid (cheaper)* — rejected: keeps the safe-by-default posture; only exact `low`/`medium` route down.
  - *Engine validation of `--risk` values* — still deferred (v0013 rationale holds: unrecognized values fall through to the most thorough tier).
- Consequences:
  - **Engine change:** `sync-agents` + `EXECUTOR_DEFAULTS` + a validate drift warning in `scripts/workflow.py`. Machinery: six tier agent files (two retired), the `do-next-slice` / `do-whole-phase` / `review-phase` / `update-workspace` skill bodies (+ Codex mirrors), the contract (`CLAUDE.md`/`AGENTS.md`), `.codex/config.toml`, `.gitignore` (adds `.env`), and the new `.env.example`. Installer: `FIXED_LIVE_FILES`/`MANAGED_FILES` swaps, `.env.example` emission (classed machinery on update), `OBSOLETE_MACHINERY` stale flagging, tier-aware post-install hints, `WORKSPACE_VERSION = 7` + the `## v7` CHANGELOG entry. `tests/retrofit_smoke.sh` asserts the 3+3 tier files, per-tier model/effort defaults, legacy-file absence, `.env.example`, and a green `sync-agents --check` on a fresh install (defaults dict == shipped files). Ships as workspace v7.
  - **Cost posture change, made explicit:** `medium` risk — the `new-slice` default — moves from opus to sonnet, and `low` moves from opus @ `high` to haiku. Quality is preserved by the literal low tier with its hair-trigger escalation, the ladder itself, and decomposition/review staying pinned to the top tier.
  - **Live smoke (2026-07-03):** all three Claude tiers spawn and respond on their shipped defaults (haiku effort-less, sonnet @ `xhigh`, opus @ `xhigh`), and `haiku` **with** `effort: high` via `.env` also spawns cleanly — the harness tolerates an effort line on haiku, so the `.env` opt-in is usable; the shipped default stays effort-less as the conservative floor.
  - Supersedes the 2026-07-01 risk-based-effort decision (two variants → three tiers) and closes the executor-model doc gap: workspace v5 had re-pinned both executors to `model: opus` in machinery (commit `1950902`) without a doc version, silently contradicting the P4 `model: inherit` record — per-tier defaults now supersede both (see *Superseded Decisions*).
- Source: operator request, 2026-07-03 (direct machinery change on `main`; no phase — durable docs versioned with the change)

### Wire `/explain` to the KB document API — API-primary save path, manual flow demoted to unreachable-only fallback (phase P6)

- Date: 2026-07-02
- Status: accepted
- Context: The knowledge repo (`~/projects/personal/knowledge`) finished its API track: a compose service on `http://localhost:8766` whose `POST /api/documents` performs, in **one locked call**, exactly what `/explain` steps 5–7 hand-rolled — writes the convention file `docs/<project>/<date>-<slug>.md` with frontmatter, inserts the Recent bullet in `docs/index.md`, upserts the SQLite row, and makes the scoped git commit `docs(<project>): add <slug>` (staging only the files it touched, never pushing). Keeping the hand-rolled steps in the skill duplicates that logic and lets it drift from the API's conventions.
- Decision:
  - **API-primary via two spelled commands.** Steps 5–7 collapse into one save step: the agent writes `body.md` (the document **without** YAML frontmatter, starting at the H1 — the API writes frontmatter itself) and `meta.json` (exactly `title` / `project` / `tags` / `source_repo` / `co_authored_by`; `date` / `slug` / `overwrite` / `commit` left at API defaults) into a temp dir, then runs a spelled `python3 -c` one-liner to merge them into `payload.json` and a spelled `curl -sS --max-time 5 … --json @payload.json http://localhost:8766/api/documents` to POST. **Quoting-safe by construction:** the document body and title never pass through shell arguments — both travel as files.
  - **Transport-vs-HTTP failure semantics.** curl exit ≠ 0 (connection refused / timeout) = the API is unreachable → fallback. Exit 0 = the API answered → branch on the status code: **201** (write NO file, do NOT touch `docs/index.md`, run NO git; report from the response's `url` / `committed` / `commit_error`), **409** duplicate (report `existing_title` / `rel_path`, ASK before retrying with `overwrite:true`), **422** (fix the payload once if the mistake is ours, else report), **401** (bearer token required). HTTP errors **never** trigger a file fallback.
  - **Bare `co_authored_by`.** The field carries the bare attribution value naming the model that did the work — the API prepends `Co-Authored-By: ` itself — replacing the commit-trailer `-m` of the old step 7.
  - **Fallback preserved verbatim.** The old manual flow (file + frontmatter template, Recent bullet after the `<!-- explain:recent -->` marker with the same missing-marker rules, the two exact `git -C` commands) survives unchanged as the fallback step, plus a Report note that a later `POST /api/reindex` — or `docker compose up -d` in the KB repo — reconciles the DB.
- Alternatives considered:
  - *Build the payload with `jq`* — rejected: the document title would pass through shell quoting (an apostrophe or colon breaks the command line); the `python3 -c` merge reads both inputs as files.
  - *Have the agent write `payload.json` directly* — rejected: that means manually JSON-escaping a ~200-line markdown body; writing `body.md` raw and merging programmatically eliminates the whole class of escaping errors.
  - *Fall back to the file write on HTTP errors* — rejected: the API is up and refusing for a reason (duplicate, convention violation, auth); a file fallback would bypass exactly the validation the API exists to enforce.
- Consequences:
  - **Ships as workspace v4.** Both live skill copies rewritten (steps renumbered 5–8; the Claude copy's `allowed-tools` extended with `Bash(curl -sS --max-time 5:*)` and `Bash(python3 -c:*)` while keeping the KB git allowance for the fallback; the sanctioned frontmatter-only difference preserved), rebuilt artifact, `WORKSPACE_VERSION = 4` + the `## v4 — 2026-07-02` `CHANGELOG.md` entry with migration notes — all one release commit (`de71eba`). The user-level `~/.claude/skills/explain/SKILL.md` was synced byte-identical afterwards (the single operator-authorized outside-repo write).

No changes to `--with-explain` gating or installer logic beyond the version constant. Steps 1–4 and the project-copy step are content-unchanged (only the PROJECT_COPY cross-reference renumbered).

- Date: 2026-07-02
- Status: accepted
- Context: Three coupled problems in the machinery. (1) The workspace pinned specific models — the `slice-executor` defs used `model: opus` and the Commit Convention + explain skill hardcoded the Codex `GPT-5.5` trailer — but a Fable/Mythos tier now sits above Opus, so the v0013 "keep `opus`, the alias auto-tracks the top model" rationale no longer holds. After this change **no slice is special-cased except `REVIEW`**, which still goes to the read-only `phase-reviewer`.
  - **A narrow `new-slice` exception for the executor.** The `slice-executor`'s hard Never-list keeps every state-transition and commit prohibition, with one carve-out: it may run `new-slice` *only while executing a decomposition slice*, to create the phase's middle slices. It still never runs `start-slice` / `finish-slice` / `set-*-status` / `new-phase` / `review-phase` / archive, never commits, and never pre-fills another slice's `plan.md` (including the middle slices it creates).
  - **Trust the `done` verdict; don't re-validate per slice.** The orchestrator no longer re-runs the slice's tests after a `done` verdict; it runs only `python3 scripts/workflow.py validate` (works/docs state-integrity, not the slice's tests) before `finish-slice` and commit. The executor still validates its own slice and reports it, and the orchestrator believes that report. The `needs_operator` / `blocked` / failed-or-empty safety halts are unchanged.
  - **Consolidate behavioral validation at the phase review.** Because per-slice re-validation is gone, the `REVIEW` slice is where the phase's slices are validated **together**: the `phase-reviewer` (and the `review-phase` checklist) re-runs each slice's validation commands plus `validate` across the finished phase. Running tests there stays read-only on files.
- Alternatives considered:
  - *Keep `DECOMP` in the orchestrator (status quo)* — rejected: its execution is exactly the context cost the orchestrator/worker split exists to avoid; the operator's explicit goal was to move it off the main thread.
  - *Have the executor only design the breakdown and let the orchestrator run `new-slice`* — rejected: slice-creation would stay in the orchestrator's context, defeating the goal; instead the executor creates the slices directly under a narrow, decomposition-only `new-slice` allowance.
  - *Skip the orchestrator's plan-mode gate for `DECOMP` (dispatch straight to the executor)* — rejected: the operator wanted the standard flow — full plan, operator approval, then executor — not a reduced one; only the execution moves, not the planning gate.
  - *Keep "verify, don't trust" (orchestrator re-runs each slice's tests)* — rejected: it duplicates the executor's just-completed validation in the orchestrator's context; one validation by the executor plus a holistic re-validation at the review is enough, and the per-slice plan-approval gate already vets each slice up front.
- Consequences:
  - No `workflow.py` engine change — routing is a skill/contract convention, and the engine never inspected a slice's `kind` to decide who runs it. The change is text: `slice-executor.md` (a decomposition branch in *Do*, the narrow `new-slice` carve-out in *Never*, trust wording), `phase-reviewer.md` and the `review-phase` skill (validate all slices together), the `do-next-slice` / `do-whole-phase` skill bodies (`.claude` ↔ `.agents`: `DECOMP` delegated, trust-don't-reverify), and the contract (`CLAUDE.md` / `AGENTS.md`). Every change is mirrored into the installer (`bootstrap_agentic_workspace.sh`), with byte-parity re-verified by `tests/retrofit_smoke.sh` (its dual-apply check is extended to the changed skills and agents). `validate` passes; no real slice was executed.
  - Amends the 2026-06-18 orchestrator/worker decision below (see *Superseded Decisions*): its "Verify, don't trust" and "Slice-kind routing — decomposition stays in the orchestrator" sub-decisions are replaced.

### Clarify the `do-whole-phase` loop, add an `auto` waiver, drop the `plan.md` template, and enter plan mode explicitly

- Date: 2026-06-20
- Status: accepted
- Context: `do-whole-phase`'s control flow read ambiguously — the per-slice "plan → approve → executor" loop and the approval-gate waiver were compressed into one dense bullet, and the waiver was only an example phrase ("run unattended") rather than a named opt-in. Separately, the orchestrator's plan step forced its plan-mode output into a fixed `plan.md` template (`Goal / Scope / Milestones / Validation`) plus per-slice `## Operator Input (verbatim)` / `## Operator Intent (refined)` headings — re-encoding the agent's native plan into a rigid form and duplicating, at the slice level, the verbatim-intent capture that `intent.md` already owns at the phase level. And although the design called for plan mode "by default", the skills only described it in prose, so Claude Code rarely actually entered plan mode — the formal plan-presentation/approval step was routinely skipped.
- Decision:
  - **Name the default loop, and what it does *not* pause on.** `do-whole-phase` advances on its own: after each slice it automatically heads into planning the next — it never pauses for permission to *start* planning. The one pause is the operator approving the **readied plan** before the executor runs: **plan → operator approves the readied plan → executor**, repeated. (`do-next-slice` does the same for its single slice.)
  - **Plan mode is entered explicitly.** Prose alone did not trigger it, so the skills now call the tools: in Claude Code the orchestrator calls `EnterPlanMode` to enter plan mode, researches read-only, then calls `ExitPlanMode` to present the readied plan for approval (its approval prompt *is* the gate); on approval the harness exits plan mode and the orchestrator writes `plan.md` and dispatches. `do-whole-phase` re-enters plan mode for each next slice. `EnterPlanMode` / `ExitPlanMode` are added to each skill's `allowed-tools`. Under `auto`, plan mode is skipped entirely (planning happens inline) — otherwise `ExitPlanMode` would force the very approval `auto` waives. (Codex has no plan mode: it presents the readied plan inline.)
  - **`auto` is the explicit waiver.** The operator invokes the skill with `auto` (e.g. `/do-whole-phase auto`; "run unattended" still counts) to skip that plan-approval pause and run plan → executor straight through. `auto` waives only the plan approval — the safety halts (`pending`, `needs_operator`, `blocked`, a failed/empty executor return) still STOP the loop. Applies to both skills.
  - **`plan.md` is the native plan, no template.** `create_slice` no longer scaffolds `plan.md` from a template (the `works/templates/plan.md` file is removed); the orchestrator writes its own free-form native plan into `plan.md` at the slice's turn, and the `slice-executor` reads it from disk as before. A fresh slice now has no `plan.md` until its turn — which tightens the existing "`DECOMP` creates bare folders, don't pre-fill `plan.md`" rule.
  - **Drop the slice-level verbatim headings.** The `## Operator Input (verbatim)` / `## Operator Intent (refined)` convention is removed; the native plan incorporates any operator note, and the operator's verbatim intent lives in the phase's `intent.md`. The refine → clarify → confirm step for an ambiguous slice note stays — its result lands in the native plan rather than a templated heading.
- Alternatives considered:
  - *Drop `plan.md` entirely and pass the plan in the executor's dispatch prompt* — rejected: the `slice-executor` runs isolated and reads its inputs from disk; keeping `plan.md` as the on-disk handoff preserves that pattern and the durable plan record.
  - *Keep the `plan.md` template* — rejected: it re-encoded the agent's native plan into a rigid form for no gain; the native plan is the plan.
  - *Make `auto` a persisted mode or engine flag* — rejected: it is a per-run operator choice, like the prior waiver; no engine change is needed.
  - *Realize plan mode by forking the skill into a `Plan` subagent (`context: fork` + `agent: Plan`)* — rejected: the orchestrator must stay on the main thread to own workflow state, commits, and the operator dialogue across the loop; a forked read-only Plan agent cannot transition state or commit, and loses the session context. Calling `EnterPlanMode` / `ExitPlanMode` from the main-thread orchestrator keeps the split intact.
- Consequences:
  - `workflow.py` `create_slice` scaffolds only `result.md`; `promote_deferred` tolerates an absent `plan.md`. `works/templates/plan.md` is deleted. The `do-next-slice` / `do-whole-phase` skill bodies (`.claude` ↔ `.agents`), `slice-executor.md`, and the contract (`CLAUDE.md` / `AGENTS.md`) are updated; every change is mirrored into the installer (`bootstrap_agentic_workspace.sh`). `validate` is unaffected — it never checked `plan.md`.
  - The `do-next-slice` / `do-whole-phase` skills gain `EnterPlanMode` / `ExitPlanMode` in `allowed-tools` (Claude frontmatter and the installer's per-skill `tools` field) and call them explicitly to drive plan mode; Codex (no plan mode, no `allowed-tools` frontmatter) presents the plan inline. No engine change. Plan mode adds an approval turn-boundary per slice by design; `auto` removes it.
  - Amends the 2026-06-18 orchestrator/worker decision below: its "Plan mode by default … operator can waive it per run" sub-decision now names that waiver `auto`, and "writes `plan.md`" now means the free-form native plan rather than a templated fill.
- Source: operator-request (direct implementation; not run through a phase)

- Context: The 2026-06-15 intent decision deliberately kept `intent.md` **convention-driven** — the agent was to write it by hand and `workflow.py` was left unchanged.   - Supersedes the "convention-driven, not a new flag" sub-decision and the "no `workflow.py` engine change" consequence of the 2026-06-15 intent decision (see *Superseded Decisions*).

### Route slice execution through a `slice-executor` subagent (orchestrator/worker split)

- Date: 2026-06-18
- Status: accepted
- Context: `do-next-slice` and `do-whole-phase` previously planned and implemented each slice inline on the main thread, so a slice's full implementation — its file reads, edits, and validation churn — accumulated in the same context that also owns workflow state, commits, and operator dialogue. As phases grow this erodes context hygiene and blurs "decide/verify" from "do". The workspace already passes cross-slice context through a file (`phase.md`), not conversation memory, so a subagent boundary behaves like the session boundary the system already survives — making an orchestrator/worker split low-risk and natural. The payoff is context hygiene plus per-slice checkpoints, not parallelism.
- Decision:
  - **Split the two execution skills into an orchestrator and a worker.** The **orchestrator** (main thread) plans each slice, writes `plan.md`, dispatches the worker, verifies the result, runs `validate`, transitions workflow state, commits, and talks to the operator. The **`slice-executor`** subagent implements exactly one already-planned slice in an isolated context: it reads `plan.md` / `phase.md` / `slice.json` / docs / code, implements, runs validation, writes `result.md`, appends cross-slice notes to `phase.md`, and returns a structured verdict (`status` = `done` | `needs_operator` | `blocked`, plus `summary` / `files_changed` / `validation` / `deviations` / `doc_versions`). One procedure, two entry points: `do-next-slice` runs it once; `do-whole-phase` loops it sequentially.
  - **Verify, don't trust.** The orchestrator re-runs `validate` and the executor's critical checks before `finish-slice` and commit; a failed or empty return means the slice is not done — do not finish, do not commit.
  - **Slice-kind routing.** Only implementation and `fix` slices are delegated. Decomposition stays in the orchestrator (it designs the breakdown and creates workflow state); review stays with the `phase-reviewer` subagent. In Codex (no subagents) the executor's procedure is followed inline via a shared-body host conditional.
  - **Plan mode by default.** The orchestrator does each slice's planning in plan-mode style first (read-only research, clarifying questions, present the plan for operator approval — the existing slice-level refine → clarify → confirm), then exits to write `plan.md` and dispatch. This makes `do-whole-phase` pause at each slice's plan gate by default; the operator can waive it per run.
  - **Full-permission executor.** `slice-executor.md` uses the `opus` model and `permissionMode: bypassPermissions` (autonomous, no prompts), at effort `max` as first shipped — later `xhigh`, then risk-based (`xhigh` default, `high` for low-risk implementation/`fix`; see the 2026-07-01 decision above). The guardrails are the orchestrator's verify-before-commit gate plus the executor's hard Never-list (no commit/push, no workflow state-transition commands, no starting/decomposing another slice).
- Alternatives considered:
  - *Keep implementing inline on the main thread* — rejected: loses the context-hygiene and per-slice-checkpoint payoff; the file-based cross-slice channel makes the subagent boundary cheap, so there is little reason not to take it.
  - *Parallel fan-out across slices (worktree isolation)* — rejected for now: slices build on each other through `phase.md` and the shared tree with a commit at each boundary, so execution is sequential; parallelism is out of scope unless a decomposition explicitly marks slices independent.
  - *Gate the plan-mode approval only on `do-next-slice` and let `do-whole-phase` run unattended* — rejected as the default: the point of the gate is to ask per slice, so both gate by default, with a per-run waiver.
  - *Keep all durable-doc writes in the orchestrator* — rejected: the executor owns `doc-new-version` for its slice (append-only, never patches old versions, coupled to the code change) and reports the versions; the orchestrator confirms via `validate`, avoiding a round-trip.
  - *Pin the executor to a fixed model id; name the dispatch tool `Task`* — corrected during implementation: the executor uses the forward-compatible `opus` model alias, and the skills allow the dispatch tool by its real name **`Agent`** — a skill cannot spawn a subagent unless `Agent` is in its `allowed-tools` (this also formalizes the previously-implicit `phase-reviewer` dispatch).
- Consequences:
  - New managed file `.claude/agents/slice-executor.md` (added to `MANAGED_FILES`); the `do-next-slice` and `do-whole-phase` skill bodies are rewritten and gain `Agent` in `allowed-tools`. The contract (`CLAUDE.md` / `AGENTS.md`) documents the orchestrator/executor model in *Driving This Workspace* and a Hard Rule. Every change was applied in the installer first, then mirrored to the materialized snapshot (`.claude` ↔ `.agents`), with byte-parity verified by re-generating from the installer; `tests/retrofit_smoke.sh` passes and no real slice was executed.
  - Codex has no subagents, so it gets no `slice-executor.md` file and executes the same procedure inline through the shared skill body's host conditional.
  - No `workflow.py` engine change: delegation is a skill/contract convention, not a machine-enforced invariant. The structured verdict is a reporting convention the orchestrator acts on (`needs_operator` → set the slice `pending` and stop; `blocked` → record and stop).
- Source: operator-request (direct implementation; not run through a phase)

### Capture operator intent at intake — refine, clarify, confirm, persist to `intent.md`

- Date: 2026-06-15
- Status: accepted
- Context: Operator requests enter the workspace as free natural language that can carry grammar slips, awkward phrasing, or genuine ambiguity. The previous flow distilled that raw text straight into a phase `--objective` (or a slice's `## Operator Input (verbatim)` note) with no refinement, no clarification, and no confirmation — so a misread of intent propagated silently into decomposition and every downstream slice, and there was no durable, authoritative record of what the operator actually asked in their own words.
- Decision:
  - **Add an intake step** at the first point intent enters a unit of work: the agent **refines** the request into clear language, **clarifies** ambiguity by asking the operator, and **confirms** the interpretation before acting. The agent does not run `new-phase` until the operator confirms.
  - **Persist both** the operator's **verbatim original** (immutable) and the **confirmed refined intent** (plus resolved clarifications) to a dedicated **`intent.md`** in the phase folder, **linked near the top of `phase.md`**. Later agents consult it whenever they are unsure of intent — it is the confirmed source of truth.
  - **Convention-driven, not a new flag.** The agent writes `intent.md` and the `phase.md` link by convention (mirroring the existing `## Operator Input (verbatim)` mechanism); `workflow.py` / `new-phase` are left unchanged. Intent applies at the **phase level always** and the **slice level when needed** — an ambiguous slice note is paired with a `## Operator Intent (refined)` section in that slice's `plan.md`.
- Alternatives considered:
  - *Store intent as a `## Intent` section inside `phase.md`* — rejected: mixes the immutable verbatim original with the evolving notebook; a separate `intent.md` keeps the original word-for-word and is the literal "store it somewhere and link from `phase.md`".
  - *Make it first-class via a `new-phase --original-input` flag (write `intent.md` + a `phase.json` field)* — rejected for now: heavier and doubles the `workflow.py` dual-apply surface; the convention path matches how operator input is already captured and keeps the engine unchanged.
  - *Phase level only* — rejected: slice-level operator notes can be just as ambiguous, so refinement is allowed there too (recorded in `plan.md`), but only when it adds value.
- Consequences:
  - The behavior lives in the **contract** (`CLAUDE.md`/`AGENTS.md`) and the `do-next-slice` / `do-whole-phase` / `retrofit` **skills**, plus a new `works/templates/intent.md`. Every change is applied in both the live files and their embedded copies inside `bootstrap_agentic_workspace.sh`, and across `.claude/skills` ↔ `.agents/skills`.
  - The installer seeds P1 with a placeholder `intent.md` (Origin `bootstrap-placeholder`, or `synthesized-from-repo` on retrofit) so every phase has the file and link uniformly; the `/retrofit` skill enriches it from project state.
  - No `workflow.py` engine change, so no new validation gate — `intent.md` presence is a contract expectation, not a machine-enforced invariant.
- Source: operator-request (direct implementation; not run through a phase)

### Support non-destructive retrofit into an existing repo via `--into-existing`

- Date: 2026-06-10
- Status: accepted
- Context: The installer only scaffolded into an empty directory — it hard-aborts when any managed file exists and refuses non-empty targets without `--force-empty-ok`, and `write_text` overwrites unconditionally. There was no supported, documented way to adopt the workspace into a repo that already has code, a README, `scripts/`, `docs/`, or git history, and no safe story for collisions with existing files.
- Decision:
  - **Extend the installer** with a flag-gated `--into-existing` retrofit mode rather than shipping a separate script or a skill-only staging dance. The fresh-install (no-flag) path stays byte-for-byte unchanged.
  - Retrofit is **non-destructive** and runs in **two passes**: a PLAN pass classifies every managed path with no writes and aborts up front on an unresolvable collision (so the tool never half-installs), then an APPLY pass writes by tier.
  - **Four-tier collision policy:** (1) *skip-if-exists* for pure content; (2) *install the `docs/` and `works/` subsystems only if wholly absent* (gate on `docs/index.json` / `works/state.json`) and gate the installer's final `rebuild`/`validate` to only-installed subsystems — because `rebuild` itself unconditionally overwrites generated files, so skip-on-write alone is insufficient; (3) *additive, idempotent merge* for `.claude/settings.json` (union permissions) and `CLAUDE.md`/`AGENTS.md` (a marked workspace section plus a `*.workspace.md` sidecar holding the full contract); (4) *hard abort* on a pre-existing `scripts/workflow.py`, since the whole runtime shells out to it.
  - **Seed P1 from project state** using only the existing `--phase-name`/`--phase-objective` flags (no `workflow.py` change); the `/retrofit` skill synthesizes them from the README/manifest/language/latest commit. P1 stays `DECOMP`+`REVIEW`-only.
  - Deliver a `retrofit` **skill** (mirrored in `.claude/skills` and `.agents/skills`, explicit-invocation only) that orchestrates preflight → installer → contract reconciliation → `validate` → report, and a committed, non-installed smoke test (`tests/retrofit_smoke.sh`).
- Alternatives considered:
  - *Skill/guide-only staging without changing the installer* — rejected: more fragile and harder to verify deterministically than a flag the installer owns.
  - *Uniform skip-if-exists for every file* — rejected: unsafe, because the installer's final `rebuild` re-overwrites generated `docs/current/*` and `works/*`; non-destructiveness is a property of write **and** rebuild together.
  - *Strict zero-touch (only ever create new files; sidecars + manual merge for everything)* — rejected in favor of additive idempotent merges for `.claude/settings.json` and the contract, for a usable out-of-box result; merges are additive-only and re-runnable with no duplication.
  - *Add an `edit-phase`/`rename-phase` command to reseed P1* — rejected: unnecessary; the existing seed flags suffice and avoid touching `workflow.py` (and its dual-apply surface).
- Consequences:
  - The installer gains a clearly flag-gated retrofit branch; the fresh path is untouched and still validated by a regression check.
  - Retrofit-only artifacts (`CLAUDE.workspace.md`, `AGENTS.workspace.md`) are deliberately **not** added to `MANAGED_FILES` (or the fresh-install guard would false-trip); the new `retrofit` skill's files **are** added so fresh installs ship it.
  - Dual-apply surface: the new skill (live files + `COMMAND_SKILLS`) and, if touched, the contract (live `CLAUDE.md`/`AGENTS.md` + the embedded `WORKFLOW_DOC`); `workflow.py` is intentionally left unchanged. A committed smoke test asserts the live↔embedded copies stay in sync.
- Source: P3 (slices P3.S1 guide+docs, P3.S2 installer mode, P3.S3 skill, P3.S4 verification)

### Phase archiving is manual and explicit, with three first-class operations

- Date: 2026-06-10
- Status: accepted
- Context: A passing phase review marks a phase `done` but should not move it out of `active/`. Operators need control over when phases leave the active set, and the original single-phase archive was framed only as an exceptional "escape hatch", leaving no supported way to archive *some* done phases while others are still in flight.
- Decision:
  - Archiving is **manual and user-requested only**, never automatic. A passing review only marks a phase `done` and leaves it in `active/`.
  - `archive-all` stays the default end-state sweep: archive every active phase at once, allowed only when **every** active phase is done (the last review slice complete).
  - `archive-phase <P>` is promoted from an exceptional escape hatch to a **first-class** single-phase archive (still gated on a passing review; `--force` only for exceptional cleanup of an unfinished phase).
  - A new **`rotate-backlog`** operation archives every phase that is currently done and leaves in-progress phases active, then rebuilds the dashboards — the partial rotation `archive-all` cannot do (it requires all phases done). Shipped as a `workflow.py` command and a skill mirrored into `.claude/skills` and `.agents/skills`.
- Alternatives considered:
  - *Auto-archive a phase when its review passes* — rejected: removes operator control and makes the active set churn mid-work; the operator explicitly wants archiving to be a deliberate step.
  - *Keep single-phase archiving as an escape hatch only* — rejected: with many phases and only some done, partial archiving is a normal need, not an exception.
  - *Add a `--dry-run`/`--force` to `rotate-backlog`* — deferred: by construction it only touches cleanly-archivable phases, so neither is needed yet; revisit if a preview is requested.
- Consequences:
  - Three archive entry points with one shared gate (`_phase_blockers`: all slices done + review `pass`): `archive-all` (full sweep), `rotate-backlog` (partial sweep), `archive-phase` (single). `rotate-backlog` reuses the existing archive helpers; no forked logic.
  - Every rule/skill/tooling change is applied in both the live repo files and their embedded copies inside `bootstrap_agentic_workspace.sh`, and `CLAUDE.md` is kept in sync with `AGENTS.md` (both generated from the same embedded contract).
- Source: P2 (slices P2.S1 engine, P2.S2 skills, P2.S3 contract, P2.S4 this record)
