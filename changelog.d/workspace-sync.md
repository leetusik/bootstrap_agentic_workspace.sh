# Workspace sync: a linked checkout keeps its workspace in hi2vi

- **Cloud mode at the command boundary.** A checkout is linked exactly when `.hi2vi/link.json` exists beside `works/` (server, org and project id; never a key). Without it every command runs exactly as before: nothing is read, no socket is opened. With it, each engine command first pulls what changed in hi2vi since `.hi2vi/base.json`'s head (a fast-forward; the generated files are rebuilt after a pull), runs unchanged against the disk, then sends every truth-file difference as one all-or-nothing batch and records the new revisions in `base.json`.
- **The truth set** is `works/**` and `docs/**` minus the generated files, `works/templates/`, the version marker, folders whose `.gitignore` is `*` and temp files. Files written outside the engine (an agent's `plan.md`, `result.md`, topics) ride the next command's batch marked `carried`; the command's own changes are marked `command`. Equal content sends nothing. `works/events.jsonl` and a loop's union logs go as appended lines, never as revisions; a folder move (archive, a deferred job's drop or promote) goes as moves paired by content, so a file's history follows it. Every batch also carries the freshly rendered `works/state.json` and `works/index.json`.
- **The client** is the standard library only: `https://` required (plain `http://` only to `localhost`, `127.0.0.1`, `::1` and `*.localhost`), 10 s timeouts, redirects never followed, the workspace key read from `$XDG_CONFIG_HOME/hi2vi/workspace-keys.json` and sent only as a Bearer header.
- **One command at a time per checkout.** A linked checkout's whole boundary (pull, command, push) runs under `fcntl.flock` on `.hi2vi/lock`, so an orchestrator and its executors running engine commands at once are serialized; a second command waits up to 120 s, then refuses with one line (the session hook waits 5 s). The lock is re-entrant within one process.
- **A journal names every interrupted state.** `.hi2vi/journal.json` reads `running` from the begin step until the commit step clears it: a command that died midway (killed, or crashed with an exception) leaves it, and the next command refuses with one line naming `sync`. Before a push it reads `pushing` with the batch ids, their bodies kept in `.hi2vi/outbox/`: a lost answer or a batch never sent is resent with the same `batch_id` at the next command, so hi2vi applies it once. A pull killed midway needs no journal: a file it wrote equals hi2vi's and reads as the same.
- **Refusals that change nothing.** With hi2vi unreachable a command is refused before it runs (`hi2vi is not reachable at <server> (<why>): in cloud mode nothing runs offline, and nothing was changed.`, exit 1, the tree untouched); a file changed on both sides refuses with `<n> files differ between this checkout and hi2vi: run sync to see them`. A push answered 409 writes nothing in hi2vi and keeps the disk: the command exits 1 with `this change is on disk but not in hi2vi (<n> conflict(s)): run sync`, even when it succeeded. `compact-resume` (the SessionStart hook) never fails on the cloud: offline, behind a held lock or after an interrupted command it runs on the disk and prints the line as a note, exit 0.
- **Batches stay under the server's limit.** A change bigger than 8,000,000 bytes as sent goes as several batches in order, each with its own `batch_id`; one file too big for any batch is refused with one line naming it, before anything is sent.
- **Migration notes.** None: an install without `.hi2vi/link.json` is unchanged.
