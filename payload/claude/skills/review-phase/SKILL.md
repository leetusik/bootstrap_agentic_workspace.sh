# review-phase

The one source for a phase review. **One review per phase**, run by `slice-executor` on the high row at the `REVIEW` slice (its playbook: `do-whole-phase/playbooks/review.md`); what the orchestrator does around it is `do-whole-phase`'s `reference/review.md`. You validate the phase's slices together (each executor's `done` was trusted, never re-run), judge the work, and write no source: fixes are fix slices. A playbook: leave a step with a stated reason.

## The boundary

The review reviews the phase, not the whole system: the product files `python3 scripts/workflow.py phase scope <P>` prints (its range, and the `pathspec=` line), the surfaces those files feed, and the claims the phase made (`intent.md`, `## Decisions`, each `result.md`). A shared file (global styles, a layout, a shared library, a manifest) widens it to every surface it feeds; a line you cannot place is inside. What you notice outside is an **observation**, a deferred-job candidate (title, reason, trigger), never a finding. The product-wide sweep is run by an operator-created QA phase, never by a review.

## Read

`CLAUDE.md`; `next`; `intent.md`; the notebook through `section` only (`<P>`, `<P> <name>`, `--topic <slug>`), with `topics/walkthrough.md`; each slice's `result.md` head-first (its verdict block) and whole where it matters; `phase scope <P>`; on a gated phase (`acceptance.required: true` in `phase.json`; `null` is undeclared, a finding) `## Operator Runtime` in `docs/current/operations.md` and `## Regression Checklist` in `docs/current/qa.md`.

## The review, in order

1. **Validate everything first.** Re-run each slice's validation commands (its verdict block, `plan.md` as fallback) plus `python3 scripts/workflow.py check`. Read each `implementation` and `fix` slice's `claims`: a listed claim with no failing-first check, or one proven by argument, is a finding (one class, *unproven claims*).
2. **The code reader is yours to dispatch**, once per phase, when `phase scope` lists product files and the operator did not say skip (your `plan.md` then reads `code reader: skipped (operator: "<their words>")`). Run `python3 scripts/workflow.py executor-route --code` and dispatch `subagent_type: code-reader` from its lines, in the background, one per repo with product files: a blind prompt of the repo path, `base` and `head` (the range `phase scope` reads), the `pathspec=` value verbatim and the output path, absolute, `topics/code-read.md` (`topics/code-read-<repo>.md` on a multi-repo host). Never the plan, a result, the notebook or a phase id. A failed or empty return is re-dispatched once; a second, or no `code-reader` agent type in the session, is `needs_operator`. Triage its findings in the same span (step 7).
3. **Run the walkthrough** (`topics/walkthrough.md`) line by line, recording each line's evidence (a command and what it printed, a screenshot path). **Drive it with `playwright-cli`**, the agent's own headless browser, you picking each next action, in place of a pre-written assertion suite, and with the product's verification skill where the repo has one. The procedure in full: `design-cowork`'s `reference/build.md`. On a gated phase run it in the runtime and access path `## Operator Runtime` names (plus the production build when they differ); that section absent or `UNFILLED` is `needs_operator`. Never pass on other slices' reports alone, and never report a walk you did not make.
4. **Walk the changed surfaces with fresh eyes** (a gated phase), as a first-time user reaching them from the entry point: everything dead, confusing or annoying there goes into the walkthrough for the operator, never into silent fixes and never judged against the design record. A design mockup, built only for a phase in which the operator asked for one, is exempt from the functional sweep: name its unwired controls. **Re-run the checklist lines inside the boundary** of `## Regression Checklist` with the same instrument; record inside/outside counts and every inside line that is not a clean pass.
5. **Nothing the phase started is left running.** List the servers, containers, listeners and browser sessions the phase's slices started (their `result.md`, `docker ps`, `lsof -iTCP -sTCP:LISTEN`, `playwright-cli list`); stop each one that is the phase's own (`docker rm -fv` for its containers) and say in `result.md` what you stopped. Never stop what the operator or another project runs.
6. **Cross-check the notebook against the logs** and route the questions. A decision a `result.md` records that `## Decisions` lost is a finding. A decision counts as present when its gist line is in `## Decisions` and its detail is in the linked topic. A dangling-pointer warning from `check` is a lost decision, a finding. **Every `## Operator Questions` entry is routed**: a decision in the walkthrough, or a deferred job you list (title, reason, trigger) for the orchestrator to file; a `(resolved → <ref>)` entry counts as routed. You may not pass with one unrouted.
7. **The code reader's findings.** Rule on every one, one line per id under `result.md`'s `## Code reader` (`C01: upheld → finding 2` / `C02: rejected — <reason>` / routed as a question): re-run a `confirmed` one's reproduction; probe a `suspected` one when cheap; reject an `unneeded change` only when `intent.md` or a decision asks for the hunk. A unit marked `not read` that carries the phase's main claim you read yourself. You may not pass with a finding unruled.
8. **Team rules** (a nested install, each repo `phase scope` shows changed): read `git -C <repo> log --format='%H%n%an <%ae>%n%B%x00' <base>..<head>` against `nested-convention [--repo <name>]` and the repo's rules files: subjects, authorship and trailers (`Co-Authored-By` only where `allowed`), no phase, slice or deferred IDs and no workspace paths in messages or branch names, the branch pattern, and `git -C <repo> ls-files -- workflow CLAUDE.local.md .claude/settings.local.json` printing nothing. Record `team-rules check:` per repo; a failed item is a finding, and nothing is rewritten without the operator's word.

## The PR step — one body per recorded branch

On whenever the phase's `pr` block records a branch or `phase scope` lists product files; skipped with no `pr` block or a waived one. For each `pr_branch=` line follow the `pr` skill (`.claude/skills/pr/SKILL.md`, read by path), its *Write and check* steps: write `topics/pr-body.md` (`topics/pr-body-<repo>.md` per repo) from the walkthrough as it ran and the final diff, plus its details file, and re-run `python3 scripts/workflow.py pr-check <P> [--repo <name>] [--branch <b>]` until `pr_check=pass` (a `warn` justified). **Writing the body is a review lens.** What it shows wrong in the code is a finding, never a silent fix. **Return `pr_bodies`**: per branch the body and details paths, the final `pr_check=` line, `size=` and `size_status`, any series line, the screenshot spots and the undecided team-rule conflicts. Product files with no branch recorded: `pr_bodies: none — <n> product files, no branch recorded`.

**A reopened phase's re-review** (its review note reads `team-reported: …` or `operator-reported: …`, from `phase reopen`): the request is the claims to verify, read with `gh pr view <n> --json reviews,comments` (read-only) or from the reopen note; at the would-pass, rewrite the body for `.claude/skills/pr/reference/reopen.md`'s update step: the same PR, never a second one.

## Findings and the verdict

**A finding is a problem class, not an instance.** Name the rule that failed, enumerate every case it governs, test each you can, and report one finding per class with its failing and passing cases. Each gets one outcome against `intent.md`: **fix now** (what the intent asks fails, something that worked broke, data lost or exposed, or the operator meets it on the walkthrough), **note** (real, filed at the pass), **drop** (one line why). A `fix now` finding names the run that shows it; a finding nobody ran is a `note` at most. A problem the base already had is an observation. Never widen the phase's promise to make a finding fixable.

**Finish the whole picture, then branch.** `pass` when no `fix now` finding is left. `changes_requested` lists the numbered findings and one proposed fix slice per class (`<P>.F<n>`, its case list as the acceptance matrix, the files of the rule's family, a `risk`: `high` when it repairs a slice whose verdict reads `route: mid` or `route: cheap`). `blocked` names the blocker. On anything but a pass, stop there.

**The closing run** (your second dispatch after a fix pass; say so in `result.md`'s title) is not a second review: it checks each fix against its matrix and commands, re-runs the validation suite, and does the pass-only work; no new hunt, no second code read. A fix that fails its matrix is `changes_requested` marked `fix did not hold: finding <k>`; a new code-level finding that breaks the intent is marked `new at the closing run: finding <k>`. Each checker runs once.

**On a pass**, update only what the phase made untrue and code cannot say: append this phase's headline checks to `## Regression Checklist` as `- [ ] <surface>: <one observable behaviour> (P<N>)`, and write an `## Operator Runtime` change, each by editing only that section of `docs/current/qa.md` or `docs/current/operations.md` (plain files). In a phase worktree (`execution.mode: "parallel"` in `phase.json`) edit no doc (two branches editing one doc conflict at the merge): put each section's exact text in `result.md` under `## Gate sections (written at merge)`, and the orchestrator writes it right after the merge. Ask for no other doc note.

## Return

Beside the card's fields: `review_verdict`; `walkthrough` (a gated phase, else `none`): the script as you ran it, each line with its result, the routed questions as decisions by the stop rules (at most about 5; the rest "decided as drawn"; about 2k characters), the deferred jobs to file, and, per repo whose bare `pr-team [--repo <name>]` prints `recorded=none`, one "decided as drawn" line with its detection and what `accept` then does; `pr_bodies`; `code_read`: the findings file(s) with upheld / rejected / routed counts, `n/a (0 product files)` or `skipped (operator: "<their words>")`; `explain`: `not written — run /knowledge:explain P<N> for a document, or ask it for a book` (an explain phase's own review publishes its unit by `do-whole-phase`'s `reference/explain-review.md`).

Commands you never run on a review slice: `review-phase`, `accept-gate`, `defer-job`, `pr-branch`, `pr-record`, `pr-rules-decide --rule`, `pr-sync`, `pr-team --record`, `phase reopen`; never push, never `gh pr create|comment|edit|ready|merge`. Yours are `check`, `phase scope`, `pr-check`, bare `pr-team`, `executor-route --code`, and on a pass the edit of the two doc sections.
