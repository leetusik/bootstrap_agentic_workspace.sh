# do-whole-phase — the phase review, its verdict and the doc debt

- Durable-doc versioning happens **in a docs phase the operator creates**, not in this phase: no slice runs `doc-new-version` (the review's two named gate sections excepted) — when a slice changes durable truth it appends a one-line "Doc impact" note to `phase.md`, the review verifies that list, and the engine stamps `consolidation: pending` until a docs phase pays it (`docs-debt` for the worklist, `/create-phase`'s docs-phase route to start it, `docs-consolidated <P>` to record it). **In a phase worktree even the gate sections wait**: the branch review records them as `## Doc impact` notes tagged `(gate section — written at merge)`, and the post-merge step on the default stream writes exactly those (`parallel-merge-finish` → `doc-new-version` for the tagged notes → `rebuild-docs`); the rest of the list waits for the docs phase, which records `parallel-consolidated <P>`. Doc versions come from one shared index.
- When you reach the phase review slice, resolve it with `executor-route <P>.REVIEW` (the high row) like any slice and delegate it to `slice-executor`. Plan it so the executor validates all of the phase's slices together (each slice's validation commands plus `python3 scripts/workflow.py validate`), reviews against the objective / `intent.md` / docs, and — **on a passing review** — verifies that the phase's "Doc impact" list is complete, appending any missing line itself (`doc_impact_added:`, never a finding on its own), returning `doc_versions: none — deferred to a docs phase` (writing only its two named gate sections, never source). **In a phase worktree** (the phase carries an `execution` block with `mode: "parallel"`, because the operator asked for one) it writes no doc versions at all, records the two gate sections as `## Doc impact` notes tagged `(gate section — written at merge)`, and returns `doc_versions: none — deferred to post-merge consolidation (parallel mode)`. A **non-passing verdict stops the executor** before those pass-only steps and hands the phase back to you: it completes validation and judgment first (so you receive the whole picture in one cycle, not one finding per cycle), then returns the verdict with numbered findings and proposed fix slices rather than doing any pass-only work. The review does **not** produce a phase explainer — explaining is a separate operation the operator runs. **When the phase's gate is `required: true`**, plan the review to run the gate stages too: the executor opens the running product itself in the `## Operator Runtime` manifest runtime and spot-checks the phase's headline claims (never passing on other slices' reports alone), walks the surfaces the phase changed with fresh eyes as a first-time user, re-runs the `## Regression Checklist` lines inside the phase's boundary (`python3 scripts/workflow.py phase-scope <P>` — its own surfaces plus every earlier line a changed file feeds, never the whole list) and appends this phase's headline checks, and routes every `## Operator Questions` entry into the walkthrough or into a deferred job for you to file (a collapsed `(resolved → <ref>)` entry counts as routed) (see the `review-phase` skill). Put `phase-scope <P>`'s output (or the command) in the review's `plan.md`, and never plan the review to re-run the whole list — a plan that says "N lines, read it whole, re-run all of it" is exactly what the boundary rule retires; whatever the review notices outside the boundary comes back as deferred-job candidates for you to file, never as findings. Name each code reader findings file in that `plan.md` too (`topics/code-read.md`, or `topics/code-read-<repo>.md` per repo; *The code reader, before the review* below), or write `code reader: n/a (0 product files)`, or, on the operator's skip, `code reader: skipped (operator: "<their words>")`. **In a nested install** plan the **team-rules check** too: a read-only pass (`git log`, `gh pr view`; it never creates or edits a pull request) over each repo the phase touched, per `phase-scope <P>` (the host in a single-repo install; skipped at-root), against that repo's recorded conventions and rules files, written into `result.md` as `team-rules check:` (`n/a (0 product files)` when the phase touched none). A failed item is a finding with a fix slice, and a history rewrite waits for the operator's word; the `review-phase` skill has the list. It returns a `review_verdict`, the fixed `explain: not written — run /knowledge:explain P<N> for a document, or ask it for a book` pointer, and — on a gated phase — a **`walkthrough`**. An explain phase's review (`## Explain` in `intent.md`) is planned from `reference/explain-review.md`: it publishes the unit (a document, a chapter or a book) private and reads it in the reader.
- **On `pass` with a required acceptance gate, the loop ends before the verdict is recorded.** Run `python3 scripts/workflow.py accept-gate <P> --open --walkthrough "<the walkthrough the executor returned>"` (on a phase with PR bodies, after the PR reader and once the drafts are open, the walkthrough opening with the draft URLs and the PR report: *The PR step* below) — the phase goes `pending` — file any deferred jobs the review listed, `validate`, commit, report the walkthrough to the operator (by the stop rules in the contract's `pending` rule), and STOP the loop, exactly as any `pending` item stops it. The operator walks the running product; accepting clears the gate (`python3 scripts/workflow.py accept-gate <P> --clear [--note "..."]` — theirs to run, or yours on their explicit say-so) and returns the phase to `in_progress`. On the resume run the `REVIEW` slice is still `in_progress` with its `result.md` carrying `review_verdict: pass` and the gate showing `cleared_at`. **With a draft open, the close runs around the pass** (`.claude/skills/pr/reference/close.md`): its step A first (`pr-sync <P>`, then the re-read of the live PR), where a change request found on GitHub becomes `changes_requested` and a fix round, never a pass; otherwise record the pass **without re-dispatching the review** (the drafts opened before the gate did), then its step B: `gh pr ready`, then a solo repo's merge after green CI by its own custom, or a team repo left Ready for the team. Operator-reported failures are recorded instead as `python3 scripts/workflow.py review-phase <P> --verdict changes_requested --note "operator-reported: ..."` (never refused; it resets the gate) and become `fix` slices the loop completes before re-reviewing. A waived phase, and a legacy phase with no `acceptance` block, record the verdict straight away as before, or with PR bodies once their drafts are open (below), with no stop.
- Record the verdict: `python3 scripts/workflow.py review-phase <P> --verdict pass|changes_requested|blocked --reviewer slice-executor --note "..."`, then `python3 scripts/workflow.py validate`.
- If the verdict is `changes_requested`, create the executor's proposed fix slices with `python3 scripts/workflow.py new-slice --phase <P> --slice <P.Fn> --name "..." --kind fix --risk <low|high>`, the rating the review proposed: `high` for a fix to a defect in mid-row work — its `result.md` verdict block reads `route: mid` (or a pre-v83 `route: cheap`) — because work the mid row got wrong never goes back to it, complete them (via the executor), then re-review. The review proposes one fix per problem class (the `review-phase` skill's *Findings, fix slices and re-review rounds*): copy each class's case list into its fix slice's `plan.md` as the acceptance matrix the executor proves case by case, and plan the next round as a bounded one (its number; each fix against its case list and any slice added since in full, each fix's blast radius, the validation suite; earlier results reused for what no fix touched).
- **Stop instead of another round.** When a re-review fails a problem class that already had a fix slice (the same rules failing a second time; the review marks it `repeat of round <n> finding <k>`), cut no further fix. Record the verdict, then set the `REVIEW` slice `pending --stop-kind decision --on-words "<what each answer does>"`, ask the operator by the stop rules, and STOP. The answers: one more fix with a simpler rule (set the `REVIEW` slice back to `changes_requested` and cut it as above); accept and defer the rest as a job (`defer-job`, then clear the stop to `in_progress` for one more round with that class out of scope); or cut scope (record it in `intent.md`, then clear the stop to `in_progress` for one more round against what is left).
- Only a `pass` verdict marks the phase `done` **and closes the `REVIEW` slice** — `review-phase` does both for you, so do **not** run a separate `finish-slice` for the review slice (the general "run `finish-slice` when a slice finishes" rule above does not apply to the review slice).
- A passing review leaves the phase `done` in `active/`; do **not** archive it here. Archiving is never this loop's job: it is `/rotate-backlog`'s, which pays the doc debt and archives after the docs phase it runs, or the operator's `archive-all` (once every active phase is done) or `archive-phase <P>` for one phase.

## The code reader, before the review

A phase's product change is read cold by the blind `code-reader` before the review executor is dispatched, and the review rules on every finding in the same cycle.

1. **When.** A phase whose `phase-scope <P>` lists product files gets the code reader before its review executor is dispatched, unless the operator says skip. A phase with none (a docs, explain or research phase) skips it, and the review's `plan.md` says `code reader: n/a (0 product files)`. **Only the operator's own words skip it**, for this one review round: never your judgment or an executor's, never a failed or missing reader (step 5 keeps its stops), never a skip carried over from an earlier phase or round.
2. **The dispatch**, after `start-slice <P>.REVIEW`: run `python3 scripts/workflow.py executor-route --code` and dispatch `code-reader` from its lines, prompt line 1 `slice: <P>.REVIEW`, with: the repo path, the folder `phase-scope` read (a multi-repo host: one dispatch per repo that has product files); `base` and `head`, the range `phase-scope <P>` reads; the product pathspec, the value of `phase-scope <P>`'s `pathspec=` line pasted verbatim (on a multi-repo host, that repo's `repo=<name> pathspec=` line), never a guessed `.`; the purpose, one plain sentence from the phase's objective, with no phase or slice id and no workspace vocabulary; and the output path, absolute, in the phase folder's `topics/`: `topics/code-read.md` (`topics/code-read-<repo>.md` on a multi-repo host). Its span is metered, never recorded with `record-dispatch`.
3. **Then the review executor**, its `plan.md` naming each findings file. It reads the file after it has validated the slices and rules on every finding (`review-phase`'s *The code reader's findings*); a `changes_requested` from an upheld finding is handled like any other. **On the operator's skip** no reader is dispatched: the `plan.md` says `code reader: skipped (operator: "<their words>")`, quoting them, where it would name the file, and the review executor rules on no findings, returns `code_read: skipped (operator: "<their words>")`, and says in `result.md` and the walkthrough that the code was not blind-read.
4. **A re-review round** dispatches the code reader again as a re-read: its earlier output, the fix range (the commits since the head it last read), and the output path `topics/code-read-r<n>.md` for round n; after a skipped round, a first read of step 2's range instead.
5. **Failures.** A failed, empty or `blocked` reader return is re-dispatched once; a second one sets the `REVIEW` slice `pending --stop-kind other --on-words "re-dispatch the code reader"` and STOPS. **No `code-reader` agent type in this session** (Claude Code uses a new agent file at the next delegation, except in a session started before `.claude/agents/` existed or with `--disable-slash-commands`, which sees it only after a restart): set the `REVIEW` slice `pending --stop-kind operator-action --on-words "restart the session; the code reader then runs"` and STOP; never substitute another agent, and never review without the code reader unless the operator says skip (steps 1 and 3).

`pr-reader` and its `code-level` class are unchanged: it still reads the body at the PR step.

## The PR step: the reader, then the drafts open (PR rule v1)

A phase that changed product files ships as one draft PR per recorded branch. The review writes and checks each body (`review-phase`'s *The PR step*: on by scope, a review lens) by `.claude/skills/pr/SKILL.md`, read by path (the skill is explicit-invocation only), and returns `pr_bodies`; put `next`'s `pr_branch=` lines and `phase-scope <P>`'s `pathspec=` line(s) in its `plan.md`. A phase with no `pr` block, or a waived one, skips all of this.

1. **The PR reader, on a verdict that would pass.** For each body, run `python3 scripts/workflow.py executor-route --reader` and dispatch `pr-reader` (the PR body's reader, a different agent from the `code-reader` that ran before the review) from its lines, prompt line 1 `slice: <P>.REVIEW`, with: the repo path, base, head, the product pathspec (the `pathspec=` value, as for the code reader), the body and details paths, the team-rule files (or `none`), the `pr-check` output, and the output path `topics/pr-read.md` (`topics/pr-read-<repo>.md` on a multi-repo host). Compare its two-sentence read with the body's Summary. Send its findings to the review's span once (SendMessage): body-level ones for one revision of the body, code-level ones for the review to rule on (confirmed: the verdict becomes `changes_requested` with that finding; rejected: `result.md` says why). If the span is gone, re-dispatch the review on the high row with a "body revision only" addendum in its `plan.md`. Then re-run `pr-check` and the PR reader once more, and never loop past that: what is left goes to the report. **No `pr-reader` agent type in this session** (Claude Code uses a new agent file at the next delegation, except in a session started before `.claude/agents/` existed or with `--disable-slash-commands`, which sees it only after a restart): set the `REVIEW` slice `pending --stop-kind operator-action --on-words "restart the session; the reader then runs"` and STOP; never substitute another agent.
2. **The drafts open then, with no stop and no word.** Read `.claude/skills/pr/SKILL.md` by path and run its *Open the drafts* steps: push each recorded branch (`git push -u origin <branch>`, never `--force`), `gh pr create --draft`, the details comment, then `pr-record <P> --branch <b> --url <url>`. A draft names people without `@` and requests no reviewers, so it notifies nobody. `next` prints `pr_draft=due` until every branch has its URL. **An open failure** (no `gh`, auth, the network, a refused push): set the `REVIEW` slice `pending --stop-kind operator-action --on-words "<what fixing it resumes>"` and STOP; never retry with `--force`, never pass without the URL. **A refused draft** (a private repo on a free plan) is never retried as a plain PR, which notifies people: set the `REVIEW` slice `pending --stop-kind decision` for the operator's `plain` or `waive` (the pr skill's `reference/open.md`) and STOP.
3. **Then the gate, or the pass.** The report opens with the draft URL(s), each PR reader's read against the Summary, the leftover findings, the size (and, over a team limit, the split or named exception the review picked), and the team-rule conflicts in its "decided as drawn" list. **On a required gate** that report opens the walkthrough you pass to `accept-gate <P> --open`, and you STOP: the operator reads the draft on GitHub, and their `accept` clears the gate (`accept-gate <P> --clear`), then the close runs: step A, the pass, step B (above). Failures they report, in chat or on GitHub at step A, become `review-phase <P> --verdict changes_requested --note "operator-reported: ..."` and fix slices, then a re-review. **On a waived gate** record the pass once the drafts are open and report the URL(s); there is no stop, and `/do-whole-phases` goes on. The PR stays a draft until the operator's word `close` runs the close (`next`'s `pr_open=` line names it). The engine refuses the pass until every recorded branch has its URL, or `pr-record <P> --waive --note "why"` ran: waive only for a phase whose product change is not worth a PR, and say why.
4. **A PR already open** (failures the operator reported on GitHub, the close's step A, or a change request after a reopen, the team's or the operator's): the re-review rewrites the body; at its next would-pass run `.claude/skills/pr/reference/reopen.md`'s update step: push the fix commits and replace the body (`gh pr edit <n> --body-file <body>`, after `pr-check`), never a second `gh pr create` and never a force-push. **Ready and a solo repo's merge come only at the close**, on the operator's `accept` (a waived gate: `close`); a team repo's merge stays the team's. Reviewers are printed (`gh pr edit <n> --add-reviewer <login>`), never requested unasked.
5. **A change request after the phase is done** (its pass recorded, its PR open), the team's or the operator's (a waived gate's `close`, a red CI at the close, a request after Ready), on the operator's word: never `review-phase`, always `reopen-phase <P> --note "team-reported: <what>"` or `--note "operator-reported: <what>"`, by `.claude/skills/pr/reference/reopen.md`'s steps (the checkout first, then `pr-sync`, then the reopen). The fix round and its re-review run in the phase's own worktree on a nested install, and in place at root, where the PR branch is checked out (the `parallel-phase` skill's *A reopened phase*).

**A loop phase's final review** (it runs after `loop-control <P> stop`, when `loop-tick` prints `review`). Its boundary is the whole loop: the ledger summary (`loop-status <P>`), the survivors, the parked items (the review may not pass while one is open, and `review-phase` refuses the pass: each is unparked on the operator's words, `loop-unpark … --to queue|survivor|dead`, or routed to a deferred job, `defer-job` then `loop-unpark … --to deferred --pointer <DID>`), and the `## Doc impact` lines rolled up from the checkpoints. The acceptance gate is as `DECOMP` declared it. A loop in its own worktree lands and tears down through the `parallel-phase` skill (*A loop phase lands at its checkpoints*). Checkpoints (`<P>.K<j>`) are not this review; they are `run-loop`'s.
