# A decomposition slice: the orchestrator's side

The executor's side (the walkthrough first, few big slices, `slice new`, the breakdown in `topics/breakdown.md`, the sets) is `playbooks/decompose.md`. Yours:

- **Plan it at the gate** unless the operator said `auto`: it fixes the shape, risk and cost of everything after it. Dispatch it on the high row. Its plan names what a throwaway run should settle before the cut; the estimate's time comes from `dispatch-summary`'s `means` block, never a session-$ figure.
- **A visual phase with no `## Design Style` in `intent.md`:** the plan asks the operator first: suggest `build-after` or `paired` with a reason, the mockup question and the drafter (`fable` or `opus`); set the slice `pending --stop-kind decision --on-words "<their answer records the style and DECOMP cuts the slices>"` and stop. `design-only` cannot be chosen here (its apply phase needs `phase new`): that answer goes to `/create-phase`.
- **At its end**, `slice finish <P>.DECOMP` prints an `advice:` line for each middle slice left undeclared, which then runs alone (`slice deps <slice> --depends-on …` declares one). Relay the executor's `parallel:` rounds in a line of your next report and run the phase as drawn.

**In the same commit as that finish:**

1. **Declare the acceptance gate.** `gate <P> require` when the phase changes anything the operator can see, else `gate <P> waive --note "<why nothing operator-visible changes>"`. `review --verdict pass` refuses an undeclared phase. A design phase follows its mockup: one that ships a mockup takes `--require`; a `design-only` phase with none takes `--waive --note "design-only, no mockup: the operator signed each job on its canvas"`; a mockup asked for later re-declares `--require` in its commit. An explain phase declares by its unit (`next` prints `explain_unit=`): a book `--require`; a document `--waive --note "standalone explain document: published private; a v2 is cheap"`; a chapter `--waive --note "explain chapter: published private; a v2 is cheap"`.
2. **Record the phase's PR branches** (PR rule v1): `pr branch <P> [--repo <name>] --name <branch>` once per repo the phase will change, the name from `intent.md`'s `Branches:` line (or proposed from `repo convention [--repo <name>]`, no IDs, and confirmed here); a recorded base (`Branches: feat/y (base: feat/x, merges after #12)`) adds `--base <that branch>` and the body's series line follows `.claude/skills/pr/reference/stack.md`. None for a phase that changes no product file, and none in a repo it will not change: the pass waits for a draft on every recorded branch. **Size never splits a phase:** a large branch splits into PRs at the review.
