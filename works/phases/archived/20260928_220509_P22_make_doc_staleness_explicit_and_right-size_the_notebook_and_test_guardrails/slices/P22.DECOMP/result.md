## 1. The cut, and why it is two slices

`intent.md` arrives fully resolved: three operator decisions, no open questions, nothing to learn first. So this is a plain forward cut — no `research` slice, no `DECOMP2`, nothing visual.

| Slice | Covers | Kind / risk | Order |
|---|---|---|---|
| `P22.S1` | D15 (notebook budget → soft ~100k-token cap) **+** D16 (keep-tests-small → core-only) | `implementation / high` | 1 |
| `P22.S2` | D14 (doc staleness explicit: marker in `docs/index.json` + surfaced where docs are read + doctrine) | `implementation / high` | 2, `depends_on P22.S1` |

**Why D15 and D16 are one slice.** Their file sets overlap almost exactly — both edit `CLAUDE.md`, both are guardrail-relaxation doctrine, and both ride the same `installer/build.py` rebuild and the same `## v39` CHANGELOG section. Splitting them would mean two edits of the same file, two installer rebuilds, and two commits of the same shape for what the phase title itself already treats as one job ("right-size the notebook **and** test guardrails"). This is the structural argument P21.DECOMP2 used for merging R1+R2, applied to a smaller case.

**Why D14 is alone.** It is the only slice with real machinery: an index field, a write path, a listing/header surface, a cross-check against the owed `## Doc impact` notes, doctrine at every docs-reading site, and smoke probes. Splitting it into "machinery" and "doctrine" halves would ship an incoherent intermediate — a marker no rule tells anyone to read — in a repo that runs on its own contract.

**Why S1 first.** The 16 KB notebook squeeze is live: this very phase's notebook is written under it, and P21's evidence is that four slices had to compress unrelated content to land. S1 lifts it, so S2 — the notes-heavy slice — writes into a notebook that no longer forces compression. `depends_on` is advisory, but it records the real relationship.

**Why both are `high`.** Even D16, which is a single-paragraph doctrine edit, is multi-file here: this is the upstream bootstrap repo, so `CLAUDE.md` cannot change without `python3 installer/build.py` and the rebuilt `bootstrap_agentic_workspace.sh` in the same slice. The contract's "anything spanning more than one file is `high`" therefore binds every slice in this phase; there is no honest `low` here.

## 2. What DECOMP verified rather than assumed

Findings that fed the notebook's *Notes for later slices* (each note carries the file:line, so this section does not repeat them):

- **D15's blast radius is bigger than the constant.** Four machinery sites (`workflow.py:59`, `:877`, `:1038`, `:1318`) plus six prose restatements of "200 lines / 16 KB" across `CLAUDE.md`, both executor agent files, and `design-cowork/SKILL.md`. `works/templates/phase.md` states no budget — checked, so there is nothing to change there despite the plan listing it as a candidate.
- **The smoke test hard-codes the old numbers.** `tests/retrofit_smoke.sh` greps for the literal `(budget 200 / 16384)` and builds a fixture notebook that must exceed the cap. A ~400 KB cap makes "build an over-budget fixture" a different exercise; S1 has to decide the probe's new shape, which is why it is called out as a note rather than left to be discovered.
- **D16's rule lives in exactly one machinery file.** `CLAUDE.md:55`. Neither executor agent file restates it (grepped), so the edit does not fan out; `docs/current/qa.md` carries it as durable truth and gets a `## Doc impact` note only.
- **D14's index already carries two of the three marker fields.** Every `docs/index.json` version entry has `created_at` (date) and `source` (the consolidating slice id, e.g. `P21.REVIEW`); the genuinely missing field is the **commit sha**. And `rebuild_docs()` copies each version file to `docs/current/<doc>.md` verbatim *including its frontmatter* — so a generated header is a small change, not a new pipeline.
- **The staleness signal is a composition of helpers P21 already shipped.** `phases_owing_consolidation()`, `doc_impact_notes()` / `doc_impact_docs()` (best-effort note→doc mapping, unassigned rather than guessed), and the `consolidation_debt_line()` / `oversized_sections_line()` shared-one-line pattern. S2 should compose them, not re-derive them — recorded as a note.
- **One implementation choice was deliberately left open, not escalated:** whether to backfill commit shas for the ~100 existing version entries or render them "unknown (pre-v39)". It is a judgment inside S2's scope with a stated lean (best-effort, never fatal — the engine must run in a checkout without git history), so it is a note, not an `## Operator Questions` entry.
