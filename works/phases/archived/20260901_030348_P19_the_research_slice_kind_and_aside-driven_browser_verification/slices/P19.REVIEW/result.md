- `--kind research --risk low` is still *creatable* — the engine does not validate `--risk`, by

  documented shape, not a hole.

**3. Is the Aside fallback wording a loophole?** No — it holds, on both edges S2 was warned about.

- *Not decorative.* The fallback releases exactly one thing: the instrument's identity. Its own
  sentence enumerates what it does **not** release — "the same sweep, at the same viewports, in the
  same manifest runtime" — and `design-cowork` states it as "is **not** excused anything here". The
  *Never* list closes the obvious abuse: "a scripted assertion suite is no substitute for a browsing
  agent, and a workspace without Aside owes the same checks through another real browser, **never
  weaker ones**". Since a script is what the prescription displaces, a fallback that licensed one
  would have been the loophole; it does not.
- *Not a gate a Linux workspace fails.* Aside appears nowhere as a precondition. The one halt
  condition in this area is the runtime manifest's, and the axis clause explicitly keeps the
  instrument out of it. Nothing installs, bundles or invokes Aside, and the new seed field is
  optional.
- *Enforced by disclosure, which is the honest mechanism available here.* "Name the instrument you
  actually used in `result.md`" plus "never report a browser run you did not make" appear in all four
  places (skill, review skill, contract, both agent bodies), so a substitution leaves a trace in the
  record rather than passing silently.

One genuine limit, which belongs to the operator and not to a fix slice: a workspace with **no** real
browser at all (headless CI) is given no third branch. That constraint predates P19 — the v32
doctrine already presupposed a real browser — so it is not a regression, and it sits inside deferred
job **D-a** below, which is exactly the question the operator gets to answer.

## Operator questions — all three routed as deferred jobs

The gate is waived, so there is no walkthrough to fold them into: routing means `defer-job`, which
**the orchestrator runs, not me**. Title / reason / trigger:

**D-a — Decide whether the Aside fallback wording stands, or Aside becomes a hard requirement**
- *Reason:* Aside is macOS-only (desktop `.dmg`) and needs an account (free tier: 500 credits/month);
  headless operation is undocumented. v36 therefore ships prescription + fallback: a workspace that
  cannot install it owes the same sweep, viewports and manifest runtime through whatever real browser
  it has. The review judged that wording sound — it excuses no check and gates no platform — but
  whether it is what the operator *wants*, versus a hard requirement with no fallback, is theirs.
  Related edge: a workspace with no real browser at all is given no third branch.
- *Trigger:* before the first adopting workspace on Linux/CI runs a fidelity or gated-review slice.

**D-b — Install Aside and validate the MCP surface end to end against a real product**
- *Reason:* "Prescribed" currently ships **unproven**. Nobody has run Aside from an executor here;
  the surface facts (`aside mcp`, the CLI, the REPL, the `mcpServers` snippet) are cited from
  `docs.aside.com`, not executed. Installing is an operator-only outward-facing action, so no slice
  could have closed this. Until it is closed, the MCP-first recommendation rests on documentation.
- *Trigger:* the first phase with a real browsable product that needs a functional sweep or a gated
  review — or sooner, if the operator wants the doctrine proven before an adopter depends on it.

**D-c — Decide whether agent Aside runs are confined to a separate account, and write it into the
doctrine**
- *Reason:* Aside is a **real desktop browser signed into the operator's own accounts**, so an agent
  driving it can act as the operator — post, purchase, delete, send. v36 says *use Aside* and never
  *with which profile*, even though `aside --account <id>` exists. This is a safety question, not an
  availability one, which is why it is filed separately from D-a and D-b rather than merged.
- *Trigger:* before any agent drives Aside against a signed-in browser — i.e. immediately upon D-b,
  and in any case before an adopter follows the prescription on a personal machine.
