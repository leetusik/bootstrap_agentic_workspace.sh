## Decisions

_Durable cross-slice decisions. Replace a superseded line; never stack versions._

- **Shape A (split by change), not B (dogfood).** Two middle slices: S1 = the `research` kind end to
  end, S2 = the Aside change. B would have spent half the 4-slice budget proving the new kind and
  shipped change 2 as findings only, leaving the operator's stated objective unlanded. The dogfood
  was not lost: `DECOMP` did the Aside investigation and handed it down through
  `## Notes for later slices` — exactly the mechanism the `research` kind institutes.
- **This phase has no `DECOMP2`.** The operator's 4-slice cap forbids it, even though this is the
  phase generalizing the pattern. Recorded so the review does not read its absence as an omission.
- **Sequencing (spent).** Both middle slices were `implementation / high` — each edits 6-10 files and
  writes real logic plus contract prose, not the one-line-or-docs case `low` is for — and S1 ran
  first with `depends_on` saying so, because they overlap in `CLAUDE.md`, both agent bodies,
  `tests/retrofit_smoke.sh` and the rebuilt installer, and S2's changelog covers S1's half.
- **`research` routes high by *kind*, not by rating** (landed in S1). It joins `decomposition` and
  `review` in the always-high clause everywhere routing is stated; `--risk high` is still set so the
  record cannot contradict the routing, and the contract says the kind wins if they disagree.
- **`DECOMP2` has two origins**, research and `build-after`, neither a special case of the other; a
  genuine third pass is `DECOMP3` (landed in S1). `design-cowork` kept its design framing and gained
  one cross-reference bullet; the READMEs were left alone — they never enumerated slice kinds.
- **Aside is prescribed as doctrine, not integrated as tooling.** macOS-only, account required,
  headless undocumented, and not installed here — so S2 shipped **prescription + MCP-first surface +
  fallback** and claims no verified run. Nothing installs, bundles or calls Aside.
- **Instrument and runtime are different axes.** Aside *drives* the runtime `## Operator Runtime`
  records and never substitutes one; the absent/`UNFILLED` → `needs_operator` → `pending` rule stays
  about the **runtime**, and a manifest naming no instrument is not an unfilled one — without that
  clause the new seed field would become a halt condition for every adopter who never receives it.
- **One seed line, in the operations body only** — `- Browser instrument for the agent:`, optional.
  Whether Aside is installed is a per-machine fact no skill can carry; the qa seed stays free of the
  doctrine, which travels in the skills and agent bodies every workspace already gets.
- **v36 shipped in S2**: `WORKSPACE_VERSION = 36` plus a `CHANGELOG.md` `## v36` section covering both
  middle slices, with Migration notes (`sync-agents`; the engine change is purely additive; the seed
  field reaches fresh installs only, since `--update` never touches `docs/`).
- **Review verdict: `pass`** (P19.REVIEW). Re-verified rather than taken on the slices' word:
  `validate`, `retrofit_smoke.sh` **139 PASS / 0 FAIL**, `installer/build.py --check` OK; both agent
  bodies byte-identical below the frontmatter (24,038 bytes each); the engine accepts
  `--kind research` and still hard-errors on an invented kind (probed on a throwaway fresh install,
  never on P19); and the **Aside fallback wording holds** — it releases the instrument's identity and
  nothing else, and is nowhere a gate a Linux workspace fails.
- **The `## Operator Runtime` rule is genuinely untouched.** `git log -L` puts its last change at P16;
  every `UNFILLED` → `needs_operator` clause in the P19 diff survives verbatim and was only extended
  with instrument language, and the new seed field is explicitly optional.

## Operator Questions

_Questions only the operator can answer. Append only; every entry is routed at the review — folded into the acceptance walkthrough or filed with `defer-job`. An unrouted entry is a review finding._

- Aside is **macOS-only** (desktop `.dmg`) and needs an Aside account; a free tier exists (500
  credits/month). Headless operation is undocumented. So an adopting workspace on Linux/CI, or any
  operator who will not install it, cannot follow the prescription. S2 writes a fallback path from
  the existing doctrine (drive the manifest runtime by whatever real browser is available; the
  doctrine's demands, not the instrument, are what bind). **Does the operator accept that fallback
  wording, or should Aside be a hard requirement with no fallback?** (from P19.DECOMP)
- Nobody has run Aside from an executor here, so "prescribed" ships unproven. **Does the operator
  want a follow-up job filed to actually install Aside and validate the MCP surface end to end
  against a real product?** (from P19.DECOMP)
- Aside is a real desktop browser signed into the operator's own accounts, so an agent driving it can
  act as the operator. v36 says *use Aside*, never *with which profile*. **Should agent runs be
  confined to a separate Aside account (`aside --account <id>`), and should that be written into the
  doctrine?** (from P19.S2)
- **All three routed at P19.REVIEW as deferred jobs** — the gate is waived, so there is no
  walkthrough to fold them into. Title / reason / trigger for each are in
  `slices/P19.REVIEW/result.md`; the orchestrator files them with `defer-job`. The third is filed on
  its own rather than merged into the other two: it is a **safety** question (an agent acting as the
  operator), not an availability one.
