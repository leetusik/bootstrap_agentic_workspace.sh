## 2. Why this granularity

**R1 + R2 merged (the one deviation).** The sequencing constraint from S1 is "R2 must land with or before R1, never after". Three options were available: two slices ordered R2→R1, two slices ordered R1→R2 (forbidden), or one slice. One slice wins on three counts:

1. **R2's file set is a strict subset of R1's.** Both edit `CLAUDE.md`, `.claude/agents/slice-executor-{mid,high}.md`, and the `review-phase` / `do-next-slice` / `do-whole-phase` / `parallel-phase` skills (S1 §11d). Merging therefore adds **no blast radius at all** — it removes a second pass over the same eight files, and with it the second installer rebuild.
2. **It makes the constraint structural instead of procedural.** Ordered as two slices, "R2 before R1" survives only as long as nobody re-orders or re-plans; S1's own warning is that if R1 ships first, gate stage 4 silently stops appending `## Regression Checklist` rows and *nothing in `validate` would catch it*. Inside one slice the failure mode cannot occur.
3. **The intermediate state would be incoherent in a self-hosting repo.** R2 alone ("the review keeps a *narrow* write to two sections") is meaningless before deferral exists, and R1 alone is exactly the broken state above. This repo *is* the workspace, so an incoherent intermediate is read and obeyed by the very next dispatch — not a theoretical concern.

The cost is one larger slice. Its blast radius is still reviewable: it is one coherent doctrinal change (where consolidation happens) with a named, measured carve-out, and S1 §11d already enumerates every file and line. It is `high`, so it routes to `slice-executor-high`.

**R3, R4, R5 kept separate.** R3 is engine-only (`workflow.py`), R4 is doctrine/skill surface, R5 is independent of the whole deferral story. Each has a distinct file set and each can pass or fail on its own; merging any of them would only make one reviewable change less reviewable.

**Ordering R3 before R4.** Both depend on S2's generalised `consolidation` state. R4's docs-phase recipe wants to point the operator at "the phases that owe docs" — which is exactly the surface R3 builds — so R3 first lets R4 reference a command that already exists instead of describing one that does not. `depends_on` is advisory; it is recorded where the dependency is real, and `P21.S5` carries none because it genuinely has none.
