## Findings & Notes

### The five decisions — SETTLED (rationale below; S1 implements them)

**1. Who runs explain → the review executor (`slice-executor-high`), by locating the installed skill and following it.** Verified: the phase review is executed by `slice-executor-high` (`.claude/skills/review-phase/SKILL.md` head; `.claude/agents/slice-executor-high.md` / `.codex/agents/slice-executor-high.toml`). Auto-explain runs inside the review slice, on a pass, alongside doc consolidation. The machinery must **reference** the installed `explain/SKILL.md` and follow its steps — **never duplicate its body** (it would drift from the plugin). Not the orchestrator: authoring a ~500-line HTML explainer inline would bloat the main thread, the opposite of why execution is delegated.

**2. Skill detection + graceful skip → ordered search, skip never changes the verdict.** Search order for `explain/SKILL.md`: (a) project `.claude/skills/explain/SKILL.md`, (b) user `~/.claude/skills/explain/SKILL.md`, (c) plugin cache `~/.claude/plugins/cache/*/…/skills/explain/SKILL.md`, (d) marketplace clones. Not found → **skip with a note**. Found but the skill's own config probe returns `KB_STATUS=unconfigured` or `error` → **skip with a note**. Verified on this machine: `~/.claude/skills/explain/SKILL.md` exists and `~/.claude/plugins/cache/` exists (so both (b) and (c) are real paths). **The explain outcome NEVER changes the review verdict** — report it as one line in `result.md` and in the structured return (e.g. `explain: saved <url>` / `explain: skipped (skill not found)` / `explain: skipped (KB unconfigured)` / `explain: skipped-offline`).

**3. Pass-gated → explain fires only on a `pass`, after validation, alongside doc consolidation.** Matches review-phase's existing "on a passing review, consolidate docs" gate. Change-ref = **this phase** (the skill's change mode explicitly covers "a phase"). On `changes_requested`/`blocked`, no explain (just as no doc versions are cut).

**4. Executor research tools → ADD `WebSearch, WebFetch` to `.claude/agents/slice-executor-high.md` `tools:` (Claude only).** Current `tools:` = `Read, Edit, Write, Glob, Grep, Bash` — no web tools, so the skill's cited "Best practices & next steps" section would always degrade to `skipped-offline` at review. The operator's confirmed intent explicitly wants that cited section ("comparing our implementation and best practices, and suggest next steps"), and it only runs when the review executor has web tools. Adding them is safe: WebSearch/WebFetch are read-only research tools (no state mutation, no commit risk), they fit the review executor's read-heavy job, and — verified — `sync-agents`' `_patched_agent_md` rewrites only `model:`/`effort:` frontmatter, so a `tools:` edit **survives sync and does not trip `validate`'s drift check**. Only `slice-executor-high` gets them (reviews always run there); mid/low untouched. **Codex mirror asymmetry accepted:** `.codex/agents/slice-executor-high.toml` has no per-agent `tools` list (Codex governs tools via `sandbox_mode`), so its review executor can't run web research → the best-practices section degrades to `skipped-offline` there, which the skill is explicitly designed to handle. Do not invent a `tools` key for the Codex toml.

**5. KB-repo commit carve-out → narrow, scoped exception to "never commit"; KB repo only, offline fallback only; never this workspace, never push.** Three real KB states and how each behaves:
- *Unconfigured* → the skill STOPs at its step 2 → auto-explain skips. No git. ✓
- *Configured, API reachable* (the normal case; on this machine the legacy convention resolves → configured) → skill step 5 POSTs, API returns 201 and makes its **own server-side scoped commit** → **the executor runs no git at all**, so the "never commit" invariant is untouched on the API path. ✓
- *Configured, API unreachable, local KB exists* (`KB_LOCAL_FALLBACK=yes`) → skill step 6 writes the explainer into `<KB_ROOT>` and commits it with `git -C <KB_ROOT>`. This is the only path that needs a carve-out.

Settled resolution: the machinery adds a **narrow, explicit exception** to the executor's "never commit" rule — the review executor MAY run the skill's `git -C <KB_ROOT> add/commit` **only** in the **separate KB repo**, **only** as that API-unreachable offline fallback, scoped to the review slice's auto-explain; it still **never** runs `git add`/`commit` in *this* workspace repo (the orchestrator alone owns those, keeping the slice boundary clean) and **never `git push` anywhere**. Rationale: the "orchestrator owns commits" invariant exists to keep *this workspace's* slice boundary clean; a commit in a *different* git root (the KB) doesn't cross that boundary, and the skill's offline path is explicitly designed to always fall through to a durable, committed save (a save without commit isn't durable in a git-backed KB). **Codex asymmetry accepted:** the Codex review executor runs under `sandbox_mode = "workspace-write"` and cannot write outside the workspace, so both the fallback file-write and its commit fail against `<KB_ROOT>` (a git root outside the workspace) → the Codex review executor treats the fallback as an automatic skip and reports it — again matching the skill's graceful-degradation design.
